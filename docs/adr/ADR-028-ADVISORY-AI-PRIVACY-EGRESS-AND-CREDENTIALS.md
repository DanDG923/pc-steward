**Status:** Accepted

**Decision owners:** Product owner, implementation reviewer and security/privacy reviewer

**Related requirements:** `FR-AI-01–06`, `FR-BUD-01–04`, `FR-DIA-03–05`, `FR-DAT-06–07/12–15`, `AC-DAT-04/12–17`, `NFR-MNT-01–04`, `NFR-OBS-01–05`

## Context and authority

The accepted specification §§9.17–9.18, 11.5, 12.3–12.5 and 16.2 permits optional OpenAI-first explanation of a failed update or diagnostic timeline. Core use remains account/key-free. Provider opt-in and approval of the exact edited/redacted evidence are separate; submitted prompts are not saved, saved redacted explanations expire after 30 days, and credentials are excluded from config, exports, backups and logs. Current diagnostic sanitization is not proof of complete AI redaction, transport or credential lifecycle. No AI adapter, key storage, call or feature implementation is introduced by this ADR.

The owner accepted the explicit limits, route, credential and settings design below, including its v1 engineering defaults. This authorizes the design only; no live call or credential access follows. SDK version, exact model, local token/framing/profile evidence, current pricing and supported transport fields must still be verified when implementation is instructed.

## Options considered and trade-offs

| Option | Advantages | Costs and risks |
|---|---|---|
| A — Official SDK behind a narrow stateless advisory port; Windows Credential Manager (**recommended**) | Small API surface, no prompt history, external exact-name credential deletion and no encrypted key file in app backups. | Native credential interop and reset recovery must be proven; SDK defaults require explicit control. |
| B — Same advisory port; current-user DPAPI encrypted blob at a fixed app-owned leaf | Supported current-user protection with app-controlled file lifecycle. | Adds a persistent credential artifact, non-following deletion/backup exclusions and blob/metadata recovery. Viable alternative if the owner prefers it; no automatic fallback. |
| C — Hosted conversation/agent, broad tools or plaintext/environment-key fallback | Less custom orchestration. | Adds retention/action authority or leaks key selection beyond the exact reviewed target. Rejected for this scope. |

## Decision

Accept A. Application ports carry a typed single-request intent, approved immutable payload and explicit result/usage status. Domain stays deterministic without network/credential APIs. A bounded provider adapter uses the official .NET SDK with controlled HTTP transport; the exact current-user credential adapter has no provider discovery/shell interface. Desktop alone composes AI. ScheduledHost, ElevatedHelper and execution/provider-action paths have no AI-send/credential capability. New projects/references require alignment with the accepted ADR-014 extension and architecture tests in implementation; none are created here.

### Consent, redaction and exact payload approval

1. Off by default. Connect requires explicit provider disclosure and a user-entered key via a masked UI; key entry/storage does not make a billable “test” call. Default SDK environment/config credential discovery is disabled. No unrelated secret-store enumeration or account/billing/admin key is requested.
2. Explain only the selected failed-update evidence or bounded diagnostic snapshot. Collection/source consent is not AI consent. Show source coverage, time range, intended provider/endpoint/model, request/output limits, conservative reserved cost and residual-secret warning. No automatic attachment, surrounding inventory, full logs, dumps, documents, release-note fetching or chat history.
3. Project only approved minimal fields, sanitize known usernames, user/profile/UNC paths, serials/device IDs, emails, tokens/keys and control characters before preview. Existing `SanitizedDiagnosticBundle` handles some sensitive-value/path forms; it must be extended/tested, not declared sufficient for new source classes. Treat all fields including names/codes as hostile data. Drop disallowed fields; length-bounding does not replace redaction.
4. Allow editing/removal of evidence. Sanitize/validate edits again, then show the resulting **final** preview. No invisible post-approval rewrite or truncation. Include fixed instructions, model/options, effective token/byte limits and outgoing header metadata in an inspectable request view; the evidence view must correspond exactly to its canonical UTF-8 JSON body. Show permitted header names/non-secret values and a redacted authentication placeholder. The key and authentication value are never exposed in preview.
5. Freeze approved body bytes, destination, model, policy/pricing/consent versions, limits and a memory-only approval binding. Final serialization/SDK transport must be captured in mock tests and match the approved body; SDK-added evidence, telemetry/body logging or changed options invalidate approval. Reserve cost transactionally under ADR-029 before dispatch, then recheck cancellation/reset, consent and versions immediately before sending. Any edit, source refresh, endpoint/model/price/limit change or disconnect requires a fresh preview/approval/reservation review. No queued offline replay after restart.

For a diagnostic explanation, default the **editable draft evidence** to the selected incident, permitted records within the accepted inclusive +/-15-minute window and a compact source-coverage/truncation summary, not the whole potentially 8 MiB snapshot (R4). Before final preview, deterministically fit the draft to the input/byte policy: selected incident first, nearby app changes next, then other nearby records in frozen timeline order; disclose every omitted count/kind and the selected interval. If even the incident plus coverage summary cannot fit, block with an edit/limit message. The user can remove/edit records and regenerate a draft; all edits are re-sanitized and shown again. No silent post-approval reduction is permitted. For `FailedUpdate`, use only the selected job's bounded sanitized failure evidence and coverage context, not unrelated history. Source selection does not grant eligibility or imply causation.

A fixed instruction treats evidence as quoted untrusted material, asks for uncertainties and separates observed facts from hypotheses. Prompts can contain injection even after redaction: the security boundary is **no tools and no action authority**, not a claim that prompt text is safe. No model-generated command, URL, package ID, confidence or diagnosis changes match/eligibility/correlation, creates a job or reaches a runner/helper. Render output as bounded plain text with no auto-open links, scripts, HTML or executable affordance. AI failure/refusal/outage is its own advisory result; original product failures and normal manual controls remain available.

### Q1 — Accepted transport/content bounds

| Setting | Accepted contract |
|---|---|
| Endpoint | One compiled approved origin `https://api.openai.com:443` and exact POST route `/v1/responses`, subject to current official SDK/API verification. No custom URL, regional/proxy endpoint, URL user-info/query, extra organization/project routing header or secondary provider is inferred. A changed route/origin needs reviewed policy and fresh consent. |
| API mode | One foreground, non-streaming, text-only request, `store: false`, no conversation/previous-response ID, file upload, background mode, hosted tool, remote MCP or extended-cache option. Omit unnecessary identifying metadata. If a model requires unsupported retention/caching/cost behavior, block that model. |
| Input | Editable maximum input tokens, initial default 8,192 including fixed instructions/framing. Derive a compatible request-byte allowance from the reviewed model/serialization profile and this setting, within the accepted 4 MiB complete UTF-8 JSON hard bound. Validate the coupled limits on save and on the exact final payload; unknown local token/framing evidence blocks dispatch. Explain the binding token/byte/context/cost limit; never silently shorten after approval. |
| Output | Editable maximum billable output tokens, initial default 1,024 including billed reasoning/non-visible output. Derive compatible response and sanitized-saved-item allowances from this setting/profile, each within the accepted 4 MiB hard bound. Only admit settings whose complete permitted response can fit those bounds. Enforce both wire/decompressed response bounds, bounded parsing and sanitization; no fixed small response cap silently defeats a higher admitted token setting. |
| Attempts | **Owner selected: manual retries only.** One HTTP attempt per approved logical request: zero automatic retries, including SDK/HTTP resilience retries. Manual retry is a new explicit request; prior uncertain cost remains reserved. ADR-029's user-configured per-request cap (initially $0.25) covers the entire logical request. |
| Concurrency/deadline | **Owner selected: one in flight and 45-second overall timeout.** Recommend enforcing this across current-user app processes with a monotonic end-to-end deadline including response read; the 10-second connect limit is also accepted. No hidden backoff/background follow-up. Cancellation/timeout after dispatch may still be billed. |
| Response storage | Save only sanitized advisory text, created/expiry UTC, **required closed source kind and validated app-local origin ID**, and an app-local explanation ID. Use the output-setting/profile-derived per-item allowance, proposed maximum 4 MiB including metadata, and an accepted 8 MiB aggregate content cap. Make room by pruning oldest inactive items visibly; reject an unsupported configuration before a paid call. Scan clear removes `DiagnosticTimeline` items and preserves `FailedUpdate`; update-history clear does the reverse. No raw HTTP response/reasoning, echoed input or unredacted output is saved. |

The 30-day explanation retention/no-saved-prompts rule and the stated v1 byte ceilings are accepted design policy. Do not persist prompt text, serialized request, edits, request-body hashes/fingerprints or recovery drafts in SQLite/logs/temp/cache/backup. Minimal accounting IDs/pricing/usage/reservations are separate under ADR-029. Redact output afresh; it can echo sensitive input. An admitted larger answer is eligible for its matching larger saved-item allowance. If saving fails because storage is locked/full, settings changed or a profile bound is violated, display the safely bounded available result and explicitly report **not saved**; never call partial content a complete saved explanation. Saving failure does not make reliable usage uncertain or refund a bill. Keep unsaved drafts/results in bounded memory only and discard on cancel/expiry/disconnect/reset. No managed-memory/OS-dump secure-erasure guarantee is made.

TLS certificate/host validation must remain enabled. Disable automatic redirects entirely, including same-origin redirects, so authorization/body cannot follow any redirect; a 3xx is an explicit failure with possibly uncertain billing. No diagnostics export, provider-error object, exception or SDK trace may include headers/body/key. Apply response/timeout/byte limits on error paths too. Proxy/TLS interception and OS networking are not an app-level promise of an uncompromised host; never bypass system certificate validation to make a call work.

### User-editable token and spending limits — accepted settings contract

The owner selects editable **maximum input tokens**, **maximum billable output tokens**, **USD per-request spending cap** and **USD monthly spending budget**. Present these four controls together in **AI limits**, with a reset-to-defaults action. Explain that output includes any billed reasoning. Show effective token/derived-byte limits, already committed spending and conservative maximum request cost at review; a larger allowance is a ceiling, not a promise of a particular answer length. Preserve one-in-flight/manual-retry/45-second behavior and finite aggregate storage. Token edits update their coupled technical byte allowances but never automatically change money; monetary edits require an explicit save under ADR-029.

Disclose beside output settings and again in request review (R5): **raising the output allowance does not extend the 45-second deadline**. A larger answer may not finish in time; cancellation/timeout may still be billed and keep its reservation uncertain, potentially indefinitely. No token/latency relationship is promised without later model measurements. Show the cost/timeout trade-off before sending; never silently increase time or retry. This is separate from a provider-terminal incomplete answer whose actual complete usage can settle under ADR-029.

Allow deliberate decreases/increases within a verified model/context/byte profile and the configured spending/test caps. Combined input plus reserved output and required overhead must fit the model context. Token values are positive supported integers; money values are finite non-negative representable USD amounts, with zero blocking paid calls. No extra product-level dollar maximum is introduced; checked numeric representation still bounds arithmetic. If both money settings are positive, require per-request <= monthly; when either is zero, preserve both values and disable paid calls. Reject invalid/overflow/unsupported values; no unlimited mode, silent clipping or automatic budget increase. Configuration compatibility is checked on save; exact current allowance is checked again at request reservation, so spent allowance does not erase otherwise valid saved settings. A request that cannot be fully reserved is blocked with the binding limit explained, never quietly clipped.

### Coupled token/byte profile — review F1

For each supported exact model/route, require a versioned, evidence-backed serialization profile with non-negative checked functions `RequestBytes(inputLimit)`, `ResponseBytes(outputLimit)` and `SavedBytes(outputLimit)`. They bound the whole allowed JSON envelope, escaped UTF-8 text, fixed schema/metadata, and sanitizer/serialization expansion, not average English characters. Prove them for the permitted text-only shape using model/tokenizer evidence and adversarial fixtures; do not guess a universal ratio. Admit settings only if all derived budgets fit the accepted **4 MiB request, 4 MiB response and 4 MiB saved-item** maxima and **8 MiB aggregate saved-content** policy. Aggregate quota may evict older inactive content with disclosure; it cannot silently reduce an admitted per-answer allowance.

This replaces the old independent 32/64/16 KiB limits. Raising tokens raises compatible byte allowances until a verified model/context, byte or cost limit is reached. Reject incompatible settings at save with the limiting constraint; show effective budgets again in request review. Count compressed wire and expanded body bytes separately; neither may exceed its admitted bound. If actual transport/body behavior violates the profile, stop boundedly and retain uncertainty only when complete reliable usage is unavailable. Measurements must include worst-case JSON escaping, control/Unicode text, sanitizer expansion, large metadata, compressed hostile input, parsing/storage overhead, UI responsiveness and the existing NFR working-set budgets. The numeric hard maxima are accepted v1 resource limits, not verified performance or a claim every model is supported. A model/profile without adequate evidence remains unavailable.

### Local token accounting and outgoing metadata — reviews F7/F11

Use a verified local tokenizer with route/framing bounds, or a separately evidenced conservative local upper-bound method for that exact model/shape. Local counting must include fixed instructions and non-visible framing. A generic UTF-8-byte count plus guessed margin is **not accepted proof**. Official [token-counting guidance](https://developers.openai.com/api/docs/guides/token-counting), checked 2026-10-29, describes request-structure tokens not necessarily visible to a plain-text tokenizer and a network counting endpoint. PC Steward does **not** use that endpoint or send evidence for counting before approval; no auxiliary token-counting request is authorized by this ADR. Unknown bounds block the paid request. Returned usage above reservation is a breach under ADR-029, never silently normalized.

The final request view lists a closed header profile: authentication type with its value redacted, JSON content/accept types, minimal fixed app/SDK-identification values if required, optional ephemeral request ID and standard Host/body-length/framing metadata. Exclude usernames, paths, machine/device identity, account/project routing and OS/runtime telemetry unless a separately reviewed policy explicitly admits necessary metadata. Actual headers from the chosen SDK/version must be captured with mocks, audited and normalized/disabled where needed; fail adapter readiness if required hidden headers cannot satisfy the profile. Header value ordering/casing and HTTP framing need not be presented as raw wire bytes, but their allowed semantic content must be reproducible. No assertion is made here that a particular SDK currently emits a particular identifier.

Persist only validated limit values/policy version as settings, never prompt content. Freeze effective token/money limits with final payload approval and reservation. A settings/model/price change invalidates an unsent preview; it cannot mutate the bound or accounting of an already dispatched request. Tampered/restored settings are revalidated and cannot grant paid-call authority or bypass continuity. Add boundary, model-context, zero/invalid budgets, explicit increases/decreases, already-committed spend, concurrent settings/reservation, restore/tampering and default-reset fixtures alongside wire-payload equality tests. This proposal uses the owner-clarified `FR-AI-04`/`FR-BUD-01` and existing `FR-BUD-02–03`; it adds no new requirement ID, product code or live authority.

### Q8 — Accepted Credential Manager identity and lifecycle

Use one Windows **generic** credential: compiled target `PCSteward/OpenAI/ApiKey.v1`, type `CRED_TYPE_GENERIC`, persistence `CRED_PERSIST_LOCAL_MACHINE` (same current user on this computer; **not** machine-wide access). No wildcard/prefix deletion, account-selected name, username/email metadata, arbitrary adapter target or enterprise-roaming persistence. Reject empty/whitespace-bearing keys and keys larger than 2,048 UTF-8 bytes; do not truncate or log them. The credential adapter validates API field/size/error behavior before shipping. A legacy adapter migration requires an explicit closed list and tests; never scan/delete other credentials.

Microsoft documents that credential target plus type identifies an entry and local-machine persistence spans that user's logon sessions on that computer. This is the basis for the accepted decision, not proof against same-user malware or an administrator. DPAPI is the viable B alternative: use current-user protection, never `CRYPTPROTECT_LOCAL_MACHINE`; its file root/leaf and backup/deletion design would need owner acceptance instead. See [CREDENTIALW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw) and [CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

For request dispatch, retrieve the exact key only after all local send prerequisites pass; minimize its lifetime, clear mutable unmanaged buffers where possible and release native credential buffers. Explicit user-driven connection/replacement/disconnect/reset flows may perform only the exact credential lifecycle accesses required by their reviewed contract; none grants send authority or probes the store from ordinary core startup. No plaintext/protected-key copy enters app configuration, SQLite, settings export, backup, logs or diagnostics. Do not silently reconnect an orphan when consent/configuration is absent; exact-target existence discovered in deliberate connection handling signals prior-state uncertainty under ADR-029. Replacement uses the same target, does not refund spend and invalidates approvals.

At connection and in removal guidance, disclose that deleting/removing PC Steward binaries does **not** itself remove the external Credential Manager entry. Recommend **Disconnect** or completed **Factory reset** before removing the app; those actions verify exact credential absence. This is guidance for the existing deployment/removal boundary, not an installer/uninstaller feature or authority to inspect other credentials. A deliberately encountered orphan entry is handled as possible prior state under ADR-029, never silent opt-in. Local key removal is not provider-side key revocation.

Disconnect first durably disables AI/revokes consent and invalidates drafts, prevents new sends under the operation gate, safely resolves/cancels active work under ADR-029, then deletes the exact target/type and verifies absence. Treat not-found as idempotent; access/logon/unknown failures remain a visible **disconnected, credential removal incomplete** result with bounded retry, never “key removed”. No remote revocation or network call follows. Microsoft documents [CredDeleteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-creddeletew) failure distinctions; mocks must exercise them. Manual guidance can tell the owner that local deletion does not revoke the provider key.

Factory reset uses the same compiled deletion/verification operation independent of the database, under ADR-027's expanded manifest and startup barrier. Every recovery/finalization path must recheck absence; a marker must not skip it. No new store/onboarding or complete-reset claim while a credential residual remains. Scan/download/log/history clearing preserves the credential. Disconnect preserves saved redacted explanations, subject to normal expiry/reset and the source-specific scan/update-history clear rules, plus minimal accounting; disclose this before confirmation. Restoring state cannot auto-reconnect or bypass the recognized recovery/first-connection continuity checks and their disclosed external-restore limitation. OS-backed credential storage itself is outside app backup authority; PC Steward exports none of it.

### Provider storage disclosure and implementation evidence

For a Responses route, explicitly setting `store: false` avoids requesting normal response application-state storage; **it does not guarantee Zero Data Retention or deletion of provider-side abuse-monitoring data**. Show the current provider disclosure/link at connect and before first egress; never describe D4's local “no saved prompts” as a provider retention promise. Provider/account/model-specific caching and retention require review before implementation/live approval. See [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data), checked 2026-10-29.

Official guidance notes automatic SDK retries and the need to account for or disable nested retries. Therefore the installed .NET SDK/pipeline must prove the proposed one-attempt policy with a counting mock transport rather than assume defaults; see [OpenAI rate limits](https://developers.openai.com/api/docs/guides/rate-limits), checked 2026-10-29. No SDK package/version, model, live pricing, account access or ZDR eligibility is established by this source check.

## Consequences, accepted amendments and implementation gates

The single-call design is easy to consent to and account for, but strict bounds/no retries can reduce availability. Credential Manager avoids an app-owned encrypted blob and requires a new external reset category. Redaction is best effort; the owner must review evidence and residual risk each call. AI remains independently disableable and optional.

Accepted additive 2.0 extensions cover ADR-010/016 pre-preview/output redaction and forbidden prompt/body/key sinks; ADR-013/019/reset design exact external credential deletion; ADR-014 capability-limited composition; ADR-015 saved-content/accounting and backup/restore separation. Earlier documents remain the existing-implementation baseline; Task 47/relevant implementation work must carry these accepted extensions and align detailed design/evidence before shipping them. This acceptance changes no source or deployed behavior.

Tasks 67/69–70 must prove redaction of every identifier class, re-redaction after edits, final wire-body/header-profile equality, approval invalidation/races, no SDK-added evidence/hidden retries, fixed TLS route/no redirects, coupled token/context/byte/saved-item bounds and deadlines, malformed/hostile output, tool absence and no action-path influence. Test larger admitted answers received/saved without cosmetic token increases, binding-limit messages, overflow/escaping/sanitizer expansion/compression, no token-counting egress, complete-usage incomplete answers versus transport cutoff, and storage failure independent of settlement. Test missing key/refusal/outage/cancel/budget failure with core workflows usable; credential size/replace/orphan/not-found/denied/removal guidance, backup/export/log exclusions, disconnect/reset recovery/residuals; ScheduledHost/helper architecture exclusions and no environment-key discovery. Mocks/synthetic data precede any approved host test. Task 71 needs exact provider/model/payload/cost approval after the security/privacy/cost gate and enforces the separate $1 total cap. Draft acceptance grants no live call or key action.

This addendum changes how the accepted design is structured in code, not what it allows. Every rule above applies to each provider and each model:
- Q1 fixed route, the F11 closed header profile and Q8 one exact credential become per-provider values in one compiled registry: endpoint, header profile, credential target `PCSteward/<Provider>/ApiKey.v1`, and request and response format.

This build registers OpenAI only. Adding a provider is a reviewed change, needing:
- an amendment to this ADR covering privacy, retention, route and headers;
- the owner's approval of any SDK;
- the same mock-transport proofs;
- Task 69 evidence for each model;
- the Task 70 review.

Offering more than one model also needs:
- a stored model choice offered only from reviewed models;
- per-provider consent and key generations.

Neither is part of this build. Implementation: `docs/review/TASK_67_ADVISORY_AI_PLAN.md` § Provider and model registry.

## Reconsider when

Required endpoint/model behavior cannot enforce the approved bounds/privacy controls, exact wire approval cannot be proven through the SDK, credential deletion/reset recovery fails, or the owner changes providers/storage/retention. Keep AI unavailable until a revised accepted design preserves optional core use and deterministic authority.

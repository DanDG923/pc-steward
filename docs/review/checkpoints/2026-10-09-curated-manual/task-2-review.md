## Important I1 — Clean setup inventory bypasses the post-scan positive-absence check

**Location:** `src/PCSteward.Application/InventoryWorkflow.cs:478-485`; initial observation at `src/PCSteward.Application/ChocolateySetupPreparation.cs:28`.

**Trigger:** The initial health probe observes Chocolatey absent. While the awaited local scan runs, a canonical client appears or its presence becomes uncertain. The scan succeeds without warnings and does not detect the reserved catalog entry. This is possible when executable presence has changed without a corresponding WinGet/ARP registration, or after the relevant inventory provider has already collected its snapshot. The setup gate intentionally distinguishes client presence from package detection, so an empty catalog match cannot replace that health observation.

**Consequence:** `confirmChocolateyAbsent` is called again only inside the nonempty-warning branch. A clean scan can therefore proceed to exact WinGet setup preflight and return a reviewable selection despite the dedicated health observation now being Present/Unknown. COM's package-installed check and catalog detection remain useful but do not establish canonical Chocolatey client absence. This is an incorrect setup offer; preparation itself does not execute a reinstall. The existing clean-path test explicitly expects one Chocolatey health call and therefore does not exercise this transition.

**Fix:** After successful inventory and acceptable warnings, repeat the dedicated fresh absence check for every reserved setup preparation, including the zero-warning branch, before the setup query. Preserve after-await cancellation and ordinary warning refusal. Add fake-only clean-scan transitions to Present, Unknown/Partial and failed observation, asserting no setup preflight; retain an unchanged-Absent success control.

**Requirement basis:** CRD-08 / FR-PRV-03 and approved spec line 99 permit setup only for positively absent Chocolatey and reject existing or untrusted clients. The Task 2 brief says preparation resolves fixed setup “after fresh health gates.” The plan does **not literally mandate two probes or explicitly name the zero-warning branch**. This finding applies the positive-absence boundary to the concrete intervening awaited scan; it is not a claim that arbitrary repeated probes eliminate all filesystem races.

## Important I2 — Strict Chocolatey choice health is followed by query launches with the weaker layout check

**Location:** `src/PCSteward.Provider.Chocolatey/ChocolateyInstallChoices.cs:12,33`; supporting reused code: `ChocolateyInstallOperations.cs:19,52-53`, `ChocolateyProvider.cs:211-214,341-364`.

**Trigger:** The new default authority completes a strict Current/Present/Trusted health probe, then calls the ordinary `ChocolateyInstallPreflightAuthority`. Its default `WindowsChocolateyProcess` has no captured health client and calls `ResolveExecutable()` and `ValidateUnchanged(executable)` with the optional `requireCallerCannotModifyLayout` argument left false. If the canonical layout becomes caller-writable after health, or during the awaited remote search before the subsequent local-list launch, the signed fixed-path client can still pass these weaker checks. A health report contains no client identity binding that the preflight path could enforce.

**Consequence:** The newly advertised strictly trusted choice-discovery path can launch a provider query in a layout that its own strict health gate would reject and return actionable choices from that query. Canonical path, reparse, signature, signer and immediate hash checks still apply; this finding specifically concerns the skipped caller-cannot-modify-layout requirement, not arbitrary executable-path authority or an installer launch.

**Fix:** Compose choice preflight with a process/query path that explicitly revalidates strict protected-layout trust immediately before both search and local-list launches (and checks cancellation before launch). Prefer binding the captured trusted identity when appropriate. Keep the existing strict health report gate and exact fixed-feed arguments. Add fake-only launch-boundary tests where layout trust changes after health and between the two queries; reject before the affected launch.

**Requirement basis:** Task 2 explicitly requires “Chocolatey offers only Machine/Neutral with strict trust.” Approved spec lines 95-99 require protected-layout checks and distinguish strict caller-cannot-modify trust from the permissive resolver default. The wording does not prescribe a constructor design, but strict query trust is a direct requirement. The permissive process implementation predates Task 2; the finding is against its **new use as the default strict-choice composition**, not a request for an unrelated provider-wide refactor.

# Task 50 — ADR-031 Chocolatey client self-update: design mapping (rev 1)

Requirements: `FR-UPD-15`, `FR-UPD-01/03–09`, `TM-03/04/07/13`; [ADR-025](../adr/ADR-025-TYPED-OPERATION-JOBS-AND-HELPER.md), [ADR-031](../adr/ADR-031-CHOCOLATEY-CLIENT-SELF-UPDATE.md) (accepted, Option 2). Builds on [Profile V2](TASK_50_CHOCOLATEY_PROFILE_V2.md) and [design rev 6](TASK_50_HELPER_ENDPOINT_AND_NATIVE_OBSERVER.md). **Nothing here admits a route:** `HasSupportedMode` still admits only `WinGetUserExactV3`, and the compiled list holds only 2.7.5, so no client update can be offered even after admission until a second reviewed release is listed.

## 1. Key risk: can `choco upgrade chocolatey` run under the held client binding?

**Evidence.** Pinned `chocolateysetup.psm1` (commit `194ac626…`, blob `c66c1282`, re-fetched and blob-verified for this note), run by the target package's `tools/chocolateyInstall.ps1` (`Initialize-Chocolatey`):
- lines 362–391 `Install-ChocolateyFiles`: `Remove-Item -Recurse -Force -ErrorAction SilentlyContinue` on **every child** of `<root>\helpers` and `<root>\tools`; `helpers\Chocolatey.PowerShell.dll` (loaded in the running client) is instead `Move-Item`d to `Chocolatey.PowerShell.dll.old` (no `SilentlyContinue`);
- lines 396–407: `Move-Item <root>\choco.exe <root>\choco.exe.old -Force -ErrorAction SilentlyContinue` (rename of the running image);
- lines 417–423: `Copy-Item … -Force` of the new `choco.exe` and of the whole new `chocolateyInstall` subtree onto the root (errors are not suppressed);
- line 143 `Ensure-Permissions` resets the default root ACL; `Invoke-Chocolatey-Initial` (760–776) runs the **new** `choco.exe -v`; pinned `Program.cs` `RemoveOldChocoExe` and `chocolateyInstaller.psm1` lines 77–81 delete the `.old` files only on a **later** run (the running image cannot be deleted).

**Conclusion: self-upgrade cannot work under the holds.** The binding holds the engine and all 56 release files with `FileShare.Read` only (design rev 6 §4 M4). Every replacement step needs `DELETE` (rename/delete) or write access, and each such open fails with `ERROR_SHARING_VIOLATION` while our handle lacks `FILE_SHARE_DELETE`/`FILE_SHARE_WRITE`. The silent removals leave old files; the first unsuppressed `Move-Item`/`Copy-Item -Force` onto a held file fails, so the package install fails part-way. Files not held (new paths in the target release, `bin`, `lib`) may already be written: the result is a **mixed tree**. That fails closed (no listed manifest matches, every route refuses) but needs owner repair, so running under holds is rejected.

**Safe alternative (adopted): verify under holds, release all client holds at resume.** The client-update job keeps the existing stage order B → C → D under full holds, so the complete listed manifest of the installed release, ACL coverage, loader/licensing, configuration and registration are re-proven immediately before launch (stage D, compared against the stage-B identities). The upgrade launch then releases **every** binding hold (engine, release tree, hooks/extensions) once `CreateProcessW`, `AssignProcessToJobObject` **and** `ResumeThread` have succeeded — the client-update analogue of `ReleaseCodeAfterResume` (rev 6 L2). Releasing only a subset is not possible: setup.psm1 deletes or renames every child of `helpers`/`tools` and the engine. After the release the binding can launch nothing more (`CanLaunch` false). Success needs the post-update exact manifest match of the **target** release (§3.6).

**Why this is acceptable.** The engine image section is mapped before `ResumeThread`; Windows refuses writes to a file with a mapped image section, so the running engine is the verified one, and a rename only changes the path. Files the old client loads after resume (script runner, `chocolateyInstaller.psm1`, `Chocolatey.PowerShell.dll`, `tools`) remain protected by the requester-unmodifiable ACLs proven at stages B and D — the same accepted residual as the L2 hooks/extensions release, extended to the release tree **for this route only**. Administrator or independently started elevated actions stay outside the same-user threat model (Profile V2).

## 2. Residual risks (need reviewer acceptance before admission)

- **R1** Between resume and setup.psm1's replacement the release tree is protected by ACLs only, not holds (§1).
- **R2** The target nupkg's `chocolateyInstall.ps1`/`chocolateysetup.psm1` and the target `choco.exe -v` execute before PC Steward can verify anything; integrity rests on the fixed Community feed and the client's package hash check, as for every Community update under ADR-025. The post-check (§3.6) also requires the installed `lib\chocolatey\chocolatey.nupkg` to equal the listed asset length and SHA-256, which detects substitution afterwards but cannot undo side effects.
- **R3** A failure part-way leaves a mixed tree: Unverified, and every Chocolatey route refuses until the owner repairs it. No automatic repair (ADR-031 Option 3 stays rejected).
- **R4** Disclosed native side effects: default root ACL reset (`Ensure-Permissions`), machine `PATH` entry, a `chocolateyProfile` import appended to an **existing** user PowerShell profile, `bin` shim replacement, `.old` residue (§3.2), and the new client run once.
- **R5** A user `ChocolateyInstallAllowCurrentUser=true` (re-read from the registry by the scripts' environment refresh) makes setup grant the user Modify; the post-check then refuses (requester-modifiable): Unverified, route closed.
- **R6** The A-Q1 / A2-L3 / O5 host-evidence dependencies of the package route apply unchanged.

## 3. Mapping onto the code

1. **Reviewed release list.** `ChocolateyReviewedRelease` (private construction): normalized version, engine file version, asset name/length/SHA-256, engine SHA-256, the compiled file table. `ChocolateyReviewedReleases.Listed` is compiled, immutable, strictly ascending by version, unique engine and asset digests; today exactly 2.7.5 (`ChocolateyReleaseManifest2_7_5`, unchanged and still pinned to the JSON). A test-only list factory (architecture-banned from `src`) builds fixture lists. `ChocolateyClientReleasePolicy` keeps `IsClientTarget` and answers list membership; it stops being a single pin.
2. **Observer step 2.** The release is selected by the held engine's SHA-256 (exactly one listed match), then that release's full manifest must match; engine trust checks that release's file version. No extra `helpers`/`tools` file except the **residue rule**: `helpers\Chocolatey.PowerShell.dll.old` is tolerated only when its length and SHA-256 equal `helpers/Chocolatey.PowerShell.dll` of a listed release. (Root files beyond the manifest are already outside the step-2 extra-file rule; `choco.exe.old` is never executed.) Residue is not held, not fingerprinted and not part of the stage-D identity, because a later elevated client run deletes it. The observation carries the selected release; fingerprint field 4 becomes that release's asset digest (identical bytes for 2.7.5, so the goldens hold). An unlisted host release, including residue from one, still refuses.
3. **Offer rule (pure).** Offered only when the observed release is listed and a strictly newer listed release exists; the target is the newest listed release. Never a downgrade or equal release; an unlisted installed client is not offered.
4. **Route and guard.** Append `UpdateRouteContract.ChocolateyClientSelfUpdateV1` and `ReviewedProviderGuardContract.ChocolateyClientSelfUpdate`. Domain enforces shape only: schema 3, Chocolatey/ChocolateyCommunity/Machine, package ID exactly `chocolatey`, `NotControllable(ProviderScriptControlled)`, `ProviderScriptSelected`, a `choco-profile-v2:` evidence ID. Provenance is `TrustedDesktopEvidenceRequired` (not user-cache intent): the candidate comes only from the compiled list. The package-job "client target refuses" rule is unchanged.
5. **Compiled command.** `ChocolateyCompiledCommand.UpgradeClient` is built only from two list entries (observed, target) plus the frozen operation, which must name exactly those versions with target strictly newer: `upgrade chocolatey --version <target> --source https://community.chocolatey.org/api/v2/ --yes --limit-output --no-color --execution-timeout 300 --ignore-remembered-arguments --fail-on-not-installed --require-checksums`. No string reaches it from remote metadata, the database or the wire except through equality with list data.
6. **Helper and verification.** A client-update binding (`ChocolateyHeldClientBinding` purpose `ClientSelfUpdate`) accepts only `UpgradeClient`; its upgrade spec releases all holds after resume. Stage C for this route is `list chocolatey --exact` equal to the observed release (no `outdated`: the candidate is the offer rule's target, which must equal the frozen candidate). Post-update verification is a Desktop-role re-observation that must select **exactly the target release** with its full manifest (residue allowed only if it matches the **source** release), the unique `chocolatey` registration at the target version, and its archive equal to the target asset length and SHA-256. Verified only then; every other observation, refusal or cancellation is Unverified; `RestartPending` is always false.
7. **Presentation.** Application-level review sheet "Update Chocolatey to X", Verify and history texts with the §2 R4 disclosures; Desktop wiring may follow.

## 4. Safety invariants (tests pin each)

No route admission; list-only targets; never downgrade; no list entry without a reviewed manifest; test-only list factory banned from `src`; compiled argv golden; client-update binding accepts no package command and package bindings accept no client command; all holds released only after a successful resume, never before launch; no Success without an exact target manifest and asset match; restart-pending never Success.

## 5. Host evidence still needed

A-Q1/A2-L3/O5 and the exact-artifact run, as for the package route; plus, on a disposable VM (never the owner host without approval) once a second release is reviewed: the residue names after a real self-upgrade, `lib\chocolatey\chocolatey.nupkg` byte-equality with the asset, and the release-at-resume run end to end. **Owner host note:** a hand upgrade to 2.7.5 leaves `helpers\Chocolatey.PowerShell.dll.old` from the previous, unlisted release until an elevated client run imports the installer module; step 2 refuses it, so the planned host-evidence re-run should record whether it is present.

# Task 50 — ADR-031 Chocolatey client self-update: design mapping (rev 3)

Requirements: `FR-UPD-15`, `FR-UPD-01/03–09`, `TM-03/04/07/13`; [ADR-025](../adr/ADR-025-TYPED-OPERATION-JOBS-AND-HELPER.md), [ADR-031](../adr/ADR-031-CHOCOLATEY-CLIENT-SELF-UPDATE.md) (accepted, Option 2). Builds on [Profile V2](TASK_50_CHOCOLATEY_PROFILE_V2.md) and [design rev 6](TASK_50_HELPER_ENDPOINT_AND_NATIVE_OBSERVER.md). **Nothing here admits a route:** `HasSupportedMode` still admits only `WinGetUserExactV3`, and the compiled list holds only 2.7.5, so no client update can be offered even after admission until a second reviewed release is listed.

## 1. Key risk: can `choco upgrade chocolatey` run under the held client binding?

**Evidence.** Pinned `chocolateysetup.psm1` (commit `194ac626…`, blob `c66c1282`, re-fetched and blob-verified for this note), run by the target package's `tools/chocolateyInstall.ps1` (`Initialize-Chocolatey`):
- lines 362–391 `Install-ChocolateyFiles`: `Remove-Item -Recurse -Force -ErrorAction SilentlyContinue` on **every child** of `<root>\helpers` and `<root>\tools`; `helpers\Chocolatey.PowerShell.dll` (loaded in the running client) is instead `Move-Item`d to `Chocolatey.PowerShell.dll.old` (no `SilentlyContinue`);
- lines 396–407: `Move-Item <root>\choco.exe <root>\choco.exe.old -Force -ErrorAction SilentlyContinue` (rename of the running image);
- lines 417–423: `Copy-Item … -Force` of the new `choco.exe` and of the whole new `chocolateyInstall` subtree onto the root (errors are not suppressed);
- line 152 `Ensure-Permissions` (defined at 268) resets the default root ACL (unless a user override applies, §2.1); `Invoke-Chocolatey-Initial` (760–776) runs the **new** `choco.exe -v`; pinned `Program.cs` `RemoveOldChocoExe` and `chocolateyInstaller.psm1` lines 77–81 delete the `.old` files only on a **later** run (the running image cannot be deleted).

**Conclusion: self-upgrade cannot work under the holds.** The binding holds the engine and all 56 release files with `FileShare.Read` only (design rev 6 §4 M4). Every replacement step needs `DELETE` (rename/delete) or write access, and each such open fails with `ERROR_SHARING_VIOLATION` while our handle lacks `FILE_SHARE_DELETE`/`FILE_SHARE_WRITE`. The silent removals leave old files; the first unsuppressed `Move-Item`/`Copy-Item -Force` onto a held file fails, so the package install fails part-way. Files not held (new paths in the target release, `bin`, `lib`) may already be written: the result is a **mixed tree**. That fails closed (no listed manifest matches, every route refuses) but needs owner repair, so running under holds is rejected.

**Safe alternative (adopted): verify under holds, release all client holds at resume.** The client-update job keeps the existing stage order B → C → D under full holds, so the complete listed manifest of the installed release, ACL coverage, loader/licensing, configuration and registration are re-proven immediately before launch (stage D, compared against the stage-B identities). The upgrade launch then releases **every** binding hold (engine, release tree, hooks/extensions) once `CreateProcessW`, `AssignProcessToJobObject` **and** `ResumeThread` have succeeded — the client-update analogue of `ReleaseCodeAfterResume` (rev 6 L2). Releasing only a subset is not possible: setup.psm1 deletes or renames every child of `helpers`/`tools` and the engine. After the release the binding can launch nothing more (`CanLaunch` false). Success needs the post-update exact manifest match of the **target** release (§3.6).

**Why this is acceptable.** The engine image section is mapped before `ResumeThread`; Windows refuses writes to a file with a mapped image section, so the running engine is the verified one, and a rename only changes the path. Files the old client loads after resume (script runner, `chocolateyInstaller.psm1`, `Chocolatey.PowerShell.dll`, `tools`) remain protected by the requester-unmodifiable ACLs proven at stages B and D — the same accepted residual as the L2 hooks/extensions release, extended to the release tree **for this route only**. Administrator or independently started elevated actions stay outside the same-user threat model (Profile V2).

## 2. Residual risks (need reviewer acceptance before admission)

- **R1** Between resume and setup.psm1's replacement the release tree is protected by ACLs only, not holds (§1).
- **R2** The target nupkg's `chocolateyInstall.ps1`/`chocolateysetup.psm1` and the target `choco.exe -v` execute before PC Steward can verify anything; integrity rests on the fixed Community feed and the client's package hash check, as for every Community update under ADR-025. The post-check (§3.6) also requires the installed `lib\chocolatey\chocolatey.nupkg` to equal the listed asset length and SHA-256, which detects substitution afterwards but cannot undo side effects.
- **R3** A failure part-way leaves a mixed tree: Unverified, and every Chocolatey route refuses until the owner repairs it. No automatic repair (ADR-031 Option 3 stays rejected). If the release of the binding's holds after resume throws part-way, the launcher records it on the client binding (`ReleaseIncomplete`; the holder sets `AllReleased` only when every close succeeded) and the postcheck reports `ReleaseIncomplete` → Unverified (`ClientReleaseIncomplete`) whatever the re-observation shows; the package route's outcome is unchanged.
- **R4** Disclosed native side effects: default root ACL reset (`Ensure-Permissions`), machine `PATH` entry, a `chocolateyProfile` import appended to an **existing** user PowerShell profile, `bin` shim replacement, `.old` leftovers (§3a), and the new client run once.
- **R5 — ELEVATED-EXECUTION residual, narrowed by the pre-launch guard + runtime watchdog (kill within notification latency); residual: the notification/poll latency window — owner acceptance still required before admission.** See §2.1 and §2.2. The earlier wording ("the post-check then refuses") understated it: the post-check runs only after attacker-chosen code may already have executed elevated.
- **R6** The A-Q1 / A2-L3 / O5 host-evidence dependencies of the package route apply unchanged.

## 2.1 R5 in detail (rev 2, independent review HIGH)

**Confirmed order** (pinned `chocolateysetup.psm1`, blob `c66c1282`, re-fetched read-only from commit `194ac626…` and blob-verified; plus pinned `Install-ChocolateyEnvironmentVariable.ps1` and `src/Chocolatey.PowerShell/Helpers/EnvironmentHelper.cs` at the same commit). `Initialize-Chocolatey`:
1. line 137 reads `$env:ChocolateyAllowInsecureRootDirectory` and line 140 `Get-ChocolateyInstallFolder` (`[Environment]::GetEnvironmentVariable('ChocolateyInstall')`), both from the **process** environment;
2. line 149 `Set-ChocolateyInstallFolder` (taken whenever the root is the default, current `ChocolateyInstall`) calls `Install-ChocolateyEnvironmentVariable` three times → `Set-EnvironmentVariable` → `EnvironmentHelper.SetVariable` → `UpdateSession` (EnvironmentHelper.cs 218–247), which copies every non-empty value of the **process**, then the **machine** key (`HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment`), then **`HKCU\Environment`** (skipped only for SYSTEM) into the process environment;
3. line 152 `Ensure-Permissions` (268–360) then reads `$env:ChocolateyInstallAllowCurrentUser -eq 'true'` (line 321) and, if set, adds (line 329) an inheritable **Modify** ACE for `WindowsIdentity.GetCurrent()` (the elevated account, i.e. the requesting user under same-user UAC) and `Set-Acl`s the root (line 344);
4. only afterwards: line 185 `Install-ChocolateyFiles` (copies `lib\chocolatey\tools\chocolateyInstall\choco.exe` to `<root>\choco.exe` at 417–419 and the subtree at 422), lines 194–195 `Import-Module <root>\helpers\chocolateyInstaller.psm1`, and line 771 `<root>\choco.exe -v`, all elevated.

So the variable is read from the process environment, but that environment has been refreshed from **both** HKLM and HKCU immediately before. The old client's own `EnvironmentSettings.UpdateEnvironmentVariables` (machine then user variables) may also refresh before the package script; the mitigation does not depend on its call order.

**The race, stated honestly.** `HKCU\Environment` is writable by the same user without elevation. A same-user process that sets `ChocolateyInstallAllowCurrentUser=true` before step 2 makes the elevated setup grant that user Modify on the whole root at step 3; from then on an unelevated process can replace files the elevated run executes next, for example `lib\chocolatey\tools\chocolateyInstall\choco.exe` before the `Copy-Item`, `<root>\choco.exe` after it and before `choco.exe -v`, or `<root>\helpers\chocolateyInstaller.psm1` before its import. That is attacker-chosen code running elevated before any PC Steward check can run; the post-check (requester-modifiable → Unverified) only reports it afterwards. Other names pinned setup.psm1 uses to weaken or skip the ACL: `ChocolateyAllowInsecureRootDirectory` (admits a `C:\Chocolatey` root, for which `Ensure-Permissions` sets no ACL; lines 137 and 286–289) and `ChocolateyInstall` (any non-default root skips `Ensure-Permissions` entirely and redirects the install).

**Best-effort mitigation (built).** `ChocolateySetupEnvironmentReader` is the single pinned, read-only exception to the Native layer's environment/registry ban (`RegOpenKeyExW` with `KEY_QUERY_VALUE | KEY_WOW64_64KEY`, presence-only `RegQueryValueExW`, exactly the two keys and three names, never value data; architecture-tested). With the pure `ChocolateySetupEnvironmentGuard` it refuses when `ChocolateyInstallAllowCurrentUser` or `ChocolateyAllowInsecureRootDirectory` exists in `HKCU\Environment` or the machine key, a user-scope `ChocolateyInstall` exists, the reading is incomplete, or the compiled child block carries either override name or a `ChocolateyInstall` other than the observed root (the block is complete and explicit; asserted). It runs in every Helper-role client observation (stage B and the stage-D re-observation: `MachineInputsUnsupported` with detail `SetupAccessOverride`) and again inside the launcher's handle gate immediately before `CreateProcessW` (NotStarted, no process, recorded on the binding as `SetupAccessOverrideRefused`). The reader reads the helper process's own hives, which are the hives the child setup refreshes from. A machine-scope `ChocolateyInstall` is normal and is not refused (administrator-controlled, outside the same-user model).

**The guard alone narrows but cannot close the race:** the user can write the value after the last check and before setup's refresh (the old client's start-up, package download and script start). Closing it would need setup not to honour the variable, a `HKCU\Environment` ACL the user cannot change, or not running setup elevated in the user's own session; none is within PC Steward's authority. Rev 3 adds the runtime watchdog (§2.2, owner option 1, 2026-11-02), which turns the whole run into a watched window but still leaves a latency residual. **The owner must explicitly accept R5 as an elevated-execution residual (or reject the client route) before any admission.**

## 2.2 R5 runtime watchdog (rev 3, owner option 1)

**What is watched (client self-update upgrade launch only; the package route and the client `list` query are unchanged).**
- The two environment keys setup's `UpdateSession` refreshes from — `HKCU\Environment` and `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment` — through `RegNotifyChangeKeyValue(REG_NOTIFY_CHANGE_NAME | REG_NOTIFY_CHANGE_LAST_SET | REG_NOTIFY_THREAD_AGNOSTIC)`, asynchronous, one auto-reset event per key, on handles opened with `KEY_NOTIFY | KEY_WOW64_64KEY` only. This lives in the same single pinned read-only reader (`ChocolateySetupEnvironmentReader.Watch`); the presence re-read still uses `KEY_QUERY_VALUE` only. Review L1: the watch keeps each key's arming-time `KEY_QUERY_VALUE` handle and every re-read queries presence through it as well as by path (each key must still exist), so a watched key deleted (`ERROR_KEY_DELETED`, or any error) or renamed away during the run is an incomplete reading → `WatchFailedDuringRun`, never a clean reading. Test keys (below `HKCU\Software\PCSteward.Tests\`) reach it only through the architecture-banned `TryWatchForTests`, so CI never writes the real environment keys.
- The Chocolatey root (recursive) and its parent (non-recursive, which reports the root's own descriptor) through overlapped `ReadDirectoryChangesW(FILE_NOTIFY_CHANGE_SECURITY)`. Each handle is `FILE_LIST_DIRECTORY | FILE_READ_ATTRIBUTES`, `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`, `OPEN_EXISTING`, backup semantics, no reparse traversal, and must be a non-reparse directory whose final path is the requested one. Full sharing means the watch never blocks setup's `Move-Item`/`Remove-Item`/`Copy-Item` (a rename's target-parent open asks for `FILE_SHARE_READ | FILE_SHARE_WRITE` and is compatible with a `FILE_LIST_DIRECTORY` holder sharing everything).
- On every wake the watchdog re-reads the three pinned names and re-evaluates the requester's access with the job's requester token (the one the stage-B/D observation used, kept by the client binding): parent in Ancestor mode, root in Node mode, and the top-level release directories `helpers` and `tools` in Node mode with the root as parent. These checks use transient `READ_CONTROL | FILE_READ_ATTRIBUTES` opens (rights outside share checks), identity-pinned to the directories seen at arming. Deeper release directories are deliberately not opened during the run: setup deletes and recreates them (§1), an open handle would leave a delete-pending directory that blocks the recreate, and they inherit from the watched ones.

**Order and kill path.** `LaunchJob` arms every watch **before** its last pre-creation checks (the existing setup-override re-read and the watchdog's own check, both inside the handle gate immediately before `CreateProcessW`), so no change can fall between a check and the watch; a watch that cannot be armed, or a fault already visible at that check, creates no process (NotStarted). After creation, assignment and resume the watchdog thread starts (before the hold release); it wakes on any notification (re-arming it first, then checking) or every 250 ms as a backstop for a missed or coalesced notification. A watch thread that cannot be created or started records `WatchFailedDuringRun` and terminates the job at once (an unwatched run is not permitted); a directory read still incomplete when its event fired is a failed re-arm, not a busy-spinning continue (review L2). The pure `ChocolateyClientWatchdogRule` decides: an override name → `SetupOverrideDuringRun`; any requester-modifiable directory → `RootWritableDuringRun`; a failed re-arm, an incomplete reading or an unreadable verdict → `WatchFailedDuringRun` (fail closed). The first fault calls `TerminateJobObject` on the launch job (retried until it succeeds; `KILL_ON_JOB_CLOSE` remains the backstop). The watchdog is bounded by the job: it is stopped and joined after settlement and before the job handle closes, then its fault is recorded on the client binding (`WatchdogFault`).

**Outcome.** Any watchdog fault forces the postcheck to its own verdict and detail (`ClientSetupOverrideDuringRun`, `ClientRootWritableDuringRun`, `ClientWatchFailedDuringRun`) — never Verified, whatever the re-observation shows. The fixed messages say the update was stopped and that Chocolatey may be partly updated. The manual step depends on whether the folder was shown changeable by the user (independent review H1):
- `ClientSetupOverrideDuringRun` and `ClientRootWritableDuringRun`: the folder may stay changeable by the user's account indefinitely (an applied `AllowCurrentUser` grant persists), so running any choco from it in an administrator prompt — including a forced reinstall — could run tampered code elevated. The message says to remove the override variable, treat the Chocolatey folder as untrusted, **not** run choco from an administrator prompt, remove or quarantine the folder and reinstall Chocolatey using Chocolatey's official installation instructions; PC Steward will not repair it. These two messages never contain `choco upgrade` (tested).
- `ClientWatchFailedDuringRun` (the folder was never shown changeable): from an administrator prompt run `choco upgrade chocolatey --version <the version you approved> --force` (or repair Chocolatey).

PC Steward never repairs automatically and never changes a third-party ACL or key.

**Residual (still needs owner acceptance).** The watchdog reacts within notification latency (event wake plus one re-read and AccessCheck, typically milliseconds; at most the 250 ms poll if a notification is missed) plus `TerminateJobObject`. Inside that window the elevated setup can still read a just-written value and apply the Modify grant, and an unelevated process can race the grant to replace a file before the kill lands. The watchdog also cannot undo a grant that was applied (PC Steward never writes ACLs): it stops the run and reports it. So R5 is narrowed from "the whole run" to "the latency window", not closed.

*Detection is by sampling, and a fast writer can avoid it (independent review M1).* The watchdog does not see registry writes as events with their contents; it sees that a key changed (notification) and then re-reads which pinned names exist, plus a 250 ms backstop poll. A same-user process can set a pinned value and delete it again within microseconds: by the time the notification wakes the watchdog and it re-reads, the value is gone, so the reading is clean (reads follow writes), and because each wake re-arms and restarts the 250 ms wait, repeated set/delete pairs also never leave a value present at a poll. Setup's own `UpdateSession` refresh can still happen to read the value during its short lifetime. What follows differs by name:
- `ChocolateyInstallAllowCurrentUser`: if setup caught it, `Ensure-Permissions` applies a persistent Modify grant to the user on the root; that grant is a security change the root watch reports and the access re-check sees, so the run is stopped as `RootWritableDuringRun` (within the latency window above, after the grant exists).
- A user-scope `ChocolateyInstall` (or `ChocolateyAllowInsecureRootDirectory`): if setup caught it, setup skips `Ensure-Permissions` or redirects the install, which may change no ACL on the watched directories at all — a redirected install can even run elevated code from a folder the user controls. Such an effect may leave nothing the watchdog observes, so the run can finish with **no fault**; the postcheck alone then reports (a redirected install does not verify against the observed root; a skipped ACL reset over an already default root may be invisible), after any elevated side effect has happened.

Owner acceptance of R5 must therefore be informed by this: the watchdog stops runs whose effects show up as a changed requester access or a persistently visible override name, but it cannot guarantee detection of a value that existed only briefly. Option 2 below (setup under a non-user identity, so `HKCU\Environment` is never read) is the only real closure.

**Owner-facing summary.** PC Steward watches Chocolatey's folder and the two environment settings for the whole update and stops it as soon as it sees the folder become changeable by your account or a setting that weakens Chocolatey's setup. It checks by looking repeatedly, not by intercepting writes, so a program running as you that sets and removes such a setting very quickly might not be seen; if that setting made Chocolatey's setup grant your account write access, PC Steward still stops the update when the grant appears, but some settings could change where or how Chocolatey installs without leaving anything PC Steward can see. PC Steward never repairs or changes Chocolatey's folder itself. Removing this residual entirely would need the update to run under a separate system identity (option 2), which is not built.

**Recorded future alternative (option 2, not built).** Run the client's setup under a non-user identity (for example a dedicated service or virtual account, or SYSTEM through a reviewed broker) so that `UpdateSession` never reads the requesting user's `HKCU\Environment` and `WindowsIdentity.GetCurrent()` is not the requester. That would close R5 entirely, but it changes the elevation model (an elevated broker/identity outside the user session, ADR-025 boundaries) and needs its own ADR and review before any implementation.

## 3. Mapping onto the code

1. **Reviewed release list.** `ChocolateyReviewedRelease` (private construction): normalized version, engine file version, asset name/length/SHA-256, engine SHA-256, the compiled file table. `ChocolateyReviewedReleases.Listed` is compiled, immutable, strictly ascending by version, unique engine and asset digests; today exactly 2.7.5 (`ChocolateyReleaseManifest2_7_5`, unchanged and still pinned to the JSON). A test-only list factory (architecture-banned from `src`) builds fixture lists. `ChocolateyClientReleasePolicy` keeps `IsClientTarget` and answers list membership; it stops being a single pin.
2. **Observer step 2.** The release is selected by the held engine's SHA-256 (exactly one listed match), then that release's full manifest must match; engine trust checks that release's file version. The extra-file rule for `helpers`/`tools` is unchanged except for the single reviewed residue allowance in §3a. The observation carries the selected release; fingerprint field 4 becomes that release's asset digest (identical bytes for 2.7.5, so the goldens hold). An unlisted host release still refuses.
3. **Offer rule (pure).** Offered only when the observed release is listed and a strictly newer listed release exists; the target is the newest listed release. Never a downgrade or equal release; an unlisted installed client is not offered.
4. **Route and guard.** Append `UpdateRouteContract.ChocolateyClientSelfUpdateV1` and `ReviewedProviderGuardContract.ChocolateyClientSelfUpdate`. Domain enforces shape only: schema 3, Chocolatey/ChocolateyCommunity/Machine, package ID exactly `chocolatey`, `NotControllable(ProviderScriptControlled)`, `ProviderScriptSelected`, a `choco-profile-v2:` evidence ID. Provenance is `TrustedDesktopEvidenceRequired` (not user-cache intent): the candidate comes only from the compiled list. The package-job "client target refuses" rule is unchanged.
5. **Compiled command.** `ChocolateyCompiledCommand.UpgradeClient` is built only from two list entries (observed, target) plus the frozen operation, which must name exactly those versions with target strictly newer: `upgrade chocolatey --version <target> --source https://community.chocolatey.org/api/v2/ --yes --limit-output --no-color --execution-timeout 300 --ignore-remembered-arguments --fail-on-not-installed --require-checksums`. No string reaches it from remote metadata, the database or the wire except through equality with list data.
6. **Helper and verification.** A client-update binding (`ChocolateyHeldClientBinding` purpose `ClientSelfUpdate`) accepts only `UpgradeClient`; its upgrade spec releases all holds after resume. Stage C for this route is `list chocolatey --exact` equal to the observed release (no `outdated`: the candidate is the offer rule's target, which must equal the frozen candidate). Post-update verification is a Desktop-role re-observation that must select **exactly the target release** with its full manifest (a §3a leftover allowed only if it matches the **source** release), the unique `chocolatey` registration at the target version, and its archive equal to the target asset length and SHA-256. Verified only then; every other observation, refusal or cancellation is Unverified; `RestartPending` is always false.
7. **Presentation.** Application-level review sheet "Update Chocolatey to X", Verify and history texts with the §2 R4 disclosures; Desktop wiring may follow.

## 3a. Self-upgrade `.old` leftovers (decision)

**Host evidence (coordinator, 2026-11-02).** After the owner's in-place upgrade to 2.7.5, engine, all 56 manifest files and the client nupkg matched the pin exactly, but `helpers` held one unlisted file, `helpers\Chocolatey.PowerShell.dll.old`, and step 2 refused the install. This matches setup.psm1 lines 384–389 and **confirms the §1 hold analysis**: self-upgrade needs rename/delete access to in-use client files, which our `FileShare.Read` holds deny. It also confirms that the installed `lib\chocolatey\chocolatey.nupkg` equals the release asset byte for byte (§3.6 assumption).

**Options.** (a) Always refuse and report "Installed, not verified", naming the leftover and a manual step. (b) A narrowly specified reviewed allowance with a disclosed finding. PC Steward never deletes anything in the Chocolatey root (AGENTS.md limits deletion to PC Steward roots), so neither option repairs.

**Choice: (b) bounded by content, with (a) as the fallback.**
- The allowance set is compiled and closed: exactly `helpers\Chocolatey.PowerShell.dll.old`, the only `helpers`/`tools` name pinned setup.psm1 creates (root `choco.exe.old` is outside the step-2 extra-file rule and never executed). A future re-pin extends the set only by review.
- It is accepted only when its length and SHA-256 equal `helpers/Chocolatey.PowerShell.dll` of a **listed** release, and it passes the same requester-unmodifiable, reparse-free coverage as every node. Every other unlisted file, and a leftover whose bytes match no listed release (the owner host today: the previous release was unlisted), refuses.
- An accepted leftover is never silent: the observation carries a `ReleaseResidue` finding with the fixed relative path and the matching release version, shown in review, Verify and history. It is not held, not fingerprinted and not part of the stage-D identity (a later elevated client run that imports the installer module deletes it).
- The client-update postcheck additionally requires the leftover, when present, to have exactly the observed length and SHA-256 of the job's **source** release's `Chocolatey.PowerShell.dll` (compared directly: several listed releases may ship the same DLL, so the observer's disclosure match is not used for this decision). A leftover of another listed release is Unverified and named (`ClientLeftoverNotSource`); anything else is Unverified.
- Rev 2: the allowance applies to **client mode only** until the package route can disclose it; a package observation refuses the leftover like any other unlisted file. A verified client update with the leftover carries `PostUpdateVerificationNote.ClientReviewedLeftover` (never a detail), which the workflow records as `TargetVerifiedWithLeftoverMessage` and history and `ChocolateyClientUpdatePresentation.VerifiedText` show with `VerifiedLeftoverNote`; a note on any other route is Unverified.
- Fallback (a): a refusal caused by a leftover is reported as "Installed, not verified" naming the file, with the manual next step "run any Chocolatey package install or upgrade from an elevated prompt (Chocolatey removes the leftover itself), then check again". PC Steward does not offer to delete it.

## 4. Safety invariants (tests pin each)

No route admission; list-only targets; never downgrade; no list entry without a reviewed manifest; test-only list factory banned from `src`; compiled argv golden; client-update binding accepts no package command and package bindings accept no client command; all holds released only after a successful resume, never before launch; no Success without an exact target manifest and asset match; restart-pending never Success; a partial hold release is never Success; no client launch while a setup override name is visible (R5 guard, single pinned read-only reader); the client upgrade runs only under the armed R5 watchdog (arming failure or a fault at arming: NotStarted; a fault during the run: job terminated, never Verified; `KEY_NOTIFY`/`KEY_QUERY_VALUE` only, full-share read-only directory handles, no registry or ACL writes in Native); no implicit 2.7.5 (required release asset digest, single three-argument engine trust check); assign/resume faults release nothing.

## 5. Host evidence still needed

A-Q1/A2-L3/O5 and the exact-artifact run, as for the package route; plus, on a disposable VM (never the owner host without approval) once a second release is reviewed: the residue names after a real self-upgrade, `lib\chocolatey\chocolatey.nupkg` byte-equality with the asset, and the release-at-resume run end to end. **Owner host:** the current `helpers\Chocolatey.PowerShell.dll.old` comes from the previous release, which is not listed, so it still refuses under §3a unless its bytes equal the 2.7.5 `Chocolatey.PowerShell.dll` (host evidence should record its length and SHA-256); it disappears after any elevated Chocolatey command that runs a package script. Re-run host evidence afterwards.

## 7. Addendum A (Step 0): client-route wiring through protocol 2, and the wire blocker

Requirements: `FR-UPD-15`, `FR-UPD-01/03–09`, `TM-03/04/07/13`, ADR-031. Base `2461683`. This addendum plans the deferred §6 items over the **existing** protocol-2 path and records why that path cannot carry them without a protocol revision. **Result: blocked at Step 0; nothing beyond this addendum is implemented.** Nothing here admits a route (`HasSupportedMode` and `DeploymentCapabilityPolicy.CapabilityOperationAllowlist` unchanged).

### 7.1 What the existing path can carry unchanged

- **Request.** Unchanged frame (`operation = "UpdatePackage"`, payload, digest, nonce, `issuedAtUtc`); the route discriminator is the frozen operation's `RouteContract = ChocolateyClientSelfUpdateV1`, bound by `operationDigest`. No new request field.
- **A0** unchanged. **A1** route-discriminated shape: for the client route `HasExactRouteShape` uses `ChocolateyClientUpdateArguments` predicates (schema 3, Chocolatey/ChocolateyCommunity/Machine/Stable, package ID exactly `chocolatey`, `NotControllable(ProviderScriptControlled)`, `ProviderScriptSelected`, guard `ChocolateyClientSelfUpdate`, provenance `TrustedDesktopEvidenceRequired`, `choco-profile-v2:` + 64 uppercase hex = F), via a client arm of `TryGetProfileDigest` that never accepts a mixed route/guard/provenance. **A2** unchanged. **A3** unchanged code; with the allow-list unchanged the capability parser rejects an `Update/ChocolateyClientSelfUpdateV1` token, so a real G1 always refuses the client route (`RequestNotAdmitted`) — the non-admission belt. Tests past A3 inject the capability seam.
- **B** client-mode Helper-role observation of the stage-B binding (`CreateForClientUpdate`): setup-override guard (`MachineInputsUnsupported`/`SetupAccessOverride`), installed client selected by engine digest from the compiled list, full manifest, holds; Observed must carry installed = frozen installed (the source release) and fingerprint = F (endpoint defence in depth unchanged).
- **C** `ListClient` only (`list chocolatey --exact`, no `outdated`): settled, well-formed, unique record equal to the stage-B release → then the pure offer rule over the same compiled list must yield a target equal to the frozen candidate → `Matched(target)`. Query failure → `PreflightQueryFailed`; list ≠ stage-B release → `InstalledMismatch`; no strictly newer listed release or target ≠ frozen → `CandidateMismatch` (candidate null or the differing listed version). Field 17 then means "the listed target the helper derived", still equality-checked by P1/P4/P5; same deadlines, floor and settlement rules.
- **D** unchanged rules (re-observation in client mode, identity comparison with stage B, guard re-evaluated → `SetupAccessOverride` surfaces as `MachineInputsUnsupported`).
- **Launch** `UpgradeClient` through `NativeLaunchSpec.FromBinding` on the client binding: release-all-at-resume, R5 watchdog armed (client launches only), pre-creation guard refusal → `Matched ∧ NotStarted` (settled, honest). Started/NotStarted/Unknown facts 4–13 unchanged.
- **Desktop.** Interpreter client arm (same S1–S13, P1–P6, H); dispatcher a client mode of the existing route dispatcher (`Supports` stays false in practice because the workflow's `HasSupportedMode` refuses first); F′ client observation with `EvidenceId` from the fresh fingerprint; `WithLingeringMarker` extended to the client route.

### 7.2 Blocker: the watchdog fault and the incomplete hold release have no wire carrier

1. `WatchdogFault` and `ReleaseIncomplete` are recorded **only on the helper-process `ChocolateyHeldClientBinding`** (`NativeLaunchSpec.OnWatchdogStopped`/`OnReleaseFaulted`); `NativeProcessObservation` and `ChocolateyUpgradeResult` do not carry them. The binding overload of `ChocolateyClientUpdatePostcheck.Evaluate` can therefore run only in the helper, but the postcheck is a **Desktop-role** re-observation run by the desktop verifier (§3.6; fact extension rev 3 §2.1 explicitly dropped "the helper's own post-update client check"). §6's "its dispatcher calls the binding overload" is not realisable across the process split.
2. The 20 response properties (fact extension rev 3 §2) have no field for either fault, and their existing semantics cannot express them honestly: a watchdog kill reports `Started` with exit code `LaunchJob.TerminationExitCode` (1) — fail-closed only by accident (`ProviderFailed` → `Failed`, verifier skipped, H1 message lost, and wrongly "Failed" for a possibly mixed tree) — **unless the client already exited 0** while lingering descendants kept the job alive, in which case the desktop verifies and may report Success. `ReleaseIncomplete` leaves the run otherwise normal (exit 0 possible) → the desktop may verify and report Success. Both violate §4 ("a partial hold release is never Success"; "a fault during the run: never Verified").
3. Field 19 (`diagnostic`) is reviewed as non-fact text ("Diagnostic only; it never changes a fact"; rev-4 L4 lingering token is history-note-only). Making a diagnostic token decide verification is a semantic revision of the reviewed wire contract, not an implementation detail. Flags (`cancelled`, `aggregateSettlementConfirmed`, `Unknown`) would have to be misreported to force Unverified/Uncertain.
4. The desktop cannot detect the faults itself: a transient override, a failed watch and a partial release leave nothing a Desktop-role re-observation can see (§2.2 M1).

### 7.3 Smallest owner decision (one of)

- **W1 (recommended): typed response field.** Add property `clientRunFault` (closed: `None | SetupOverrideDuringRun | RootWritableDuringRun | WatchFailedDuringRun | ReleaseIncomplete`) before `diagnostic`; codec S14: non-`None` ⇒ `Matched ∧ Started`; the interpreter accepts non-`None` only for `ChocolateyClientSelfUpdateV1` and carries it in a closed, interpreter-only-constructed value on the dispatch observation; the desktop postcheck gains an overload taking that value plus the F′ source release (replacing the helper-only binding overload as the `src` entry; `EvaluateForTests` stays banned); the workflow forces Unverified with the fault's fixed message before any verification. A 21-property protocol "2" redefined in place (like O1) or a protocol "3" with a capability-file change — owner/reviewer choice.
- **W2: fixed diagnostic tokens** (closed set, emitted only by the endpoint for a client Started run, parsed only for the client route, demotion-only). No frame change, but trust-relevant data in a sanitized free-text field: a future sanitizer or truncation change fails open silently. Needs explicit review of the field-19 semantic change.
- **W3: no response after a faulted client run** (desktop Uncertain, barrier kept). No wire change, but loses the H1 recovery texts (§2.2) and leaves a reconciliation barrier; contradicts §2.2 "Outcome".

Until one is accepted, the helper item, stage rows, endpoint/interpreter/dispatcher acceptance, F′ producer and verifier wiring for this route stay unbuilt, because each would either drop the R3/R5 fault (fail open on the desktop) or invent wire semantics.

## 8. W1 field (owner-approved 2026-11-02, ADR-031 owner decision 4)

Requirements: `FR-UPD-15`, `FR-UPD-01/03–09`, `TM-03/04/07/13`, ADR-031. Base `6277ba7`. This section fixes the exact W1 contract before any code. **Nothing here admits a route**: `HasSupportedMode` and `DeploymentCapabilityPolicy.CapabilityOperationAllowlist` stay unchanged, so a real G1 refuses `ChocolateyClientSelfUpdateV1` (`RequestNotAdmitted`) and the desktop refuses it before any claim; the route stays disabled pending review and the owner's separate R5 acceptance.

### 8.1 Field

- **Name** `clientRunFault`; JSON string; **position 19** of a client-route response (immediately before `diagnostic`, which stays last). A client-route response therefore has exactly 21 properties; every other response keeps the reviewed 20.
- **Closed value set with an explicit allowed-combination table** (exact spelling, no numeric/alias/case variants; parsed by table lookup, never `Enum.Parse`):

| Wire text | Watchdog stop | Release incomplete |
|---|---|---|
| `None` | — | no |
| `SetupOverrideDuringRun` | SetupOverride | no |
| `RootWritableDuringRun` | RootWritable | no |
| `WatchFailedDuringRun` | WatchFailed | no |
| `ReleaseIncomplete` | — | yes |
| `SetupOverrideDuringRun+ReleaseIncomplete` | SetupOverride | yes |
| `RootWritableDuringRun+ReleaseIncomplete` | RootWritable | yes |
| `WatchFailedDuringRun+ReleaseIncomplete` | WatchFailed | yes |

  Any other text (two watchdog kinds, reversed order, whitespace, `None+…`, lowercase, digits) is invalid. The set is complete for the binding: `RecordWatchdogFault` keeps only the **first** watchdog fault, so at most one kind can co-occur with `ReleaseIncomplete`. Longest value 39 B (+ `,"clientRunFault":""` = 20 B overhead) → a client frame is at most 5,083 + 59 = 5,142 B ≤ 16,384 (upper bound).
- **Source.** Only the helper endpoint writes it, from the client binding's `WatchdogFault` and `ReleaseIncomplete` read after the launch settled (the watchdog is joined and its fault recorded in the launcher's `finally`, before the launch task completes), carried by `ChocolateyUpgradeResult.Observed`. Every other client-route decision (A1–D refusals, Undetermined, Matched ∧ NotStarted, a launch that threw) writes `None`.

### 8.2 Codec rule S14 (structural, added to S1–S13)

The codec is told the expected reply shape by the reader (`Package` for every existing caller and route; `ClientSelfUpdate` only when the frozen operation is `ChocolateyClientSelfUpdateV1`).
- **S14a presence:** client shape ⇒ the property is present at position 19; package shape ⇒ it is absent. A frame of the other shape fails the exact-field-set check (missing, extra or reordered property) and is rejected whole.
- **S14b value:** exactly one row of the table above.
- **S14c consistency:** a value other than `None` ⇒ `qualification = Matched` ∧ `invocation ∈ {Started, Unknown}` (a watchdog runs and the holds are released only after `ResumeThread`, so a refusal, an Undetermined or a NotStarted run can never carry one).
- `CreateResponse` throws (nothing is written; the desktop records Uncertain) and `TryReadResponse` returns false on any S14 failure. The whole-frame re-encode comparison is unchanged and covers the new property.

### 8.3 Desktop validation and the downgrade-only lattice

- Rejection path (unchanged §4.1 rule): a missing field on a client response, a field on a package response, an unknown value, an invalid combination or an S14c violation fails the codec, so the interpreter discards every wire fact → `Unknown`, unsettled → **Uncertain**, barrier kept, never Success.
- An accepted value becomes `ReviewedClientRunFault` (Application; private constructor; a single factory whose only `src` call site is the interpreter, architecture-pinned like `RecordedHelperCandidateCheck.FromDesktopDerived`), carried on `ReviewedUpdateDispatchObservation.ClientRunFault`. The interpreter sets it for every accepted client-route frame (including `None`) and never for another route.
- **Lattice (assertion strength):** `Success`/`RestartRequired` (assert the target) > `Failed` (asserts the run failed, i.e. "not updated") > `Unverified` (asserts nothing about the result) > `Uncertain` (asserts nothing; barrier kept). The existing workflow already places started-but-stopped work at `Unverified`, never "not updated". For the client route the field only moves an outcome **down** this order, never up, and never removes a barrier:

| Workflow path (client route) | Field `None` | Field non-`None` | Field null (no accepted value) |
|---|---|---|---|
| Not settled (Uncertain) | Uncertain | Uncertain + the fault's fixed recovery text appended | Uncertain |
| Settled NotInvoked (Refused/Failed/Cancelled/ElevationDenied) | unchanged | impossible (S14c); defensive: unchanged + text | unchanged |
| Settled Started: Cancelled/TimedOut/Failed/ProviderFailed/exit unknown | unchanged | **Unverified** with the fault's text (no verification) | Unverified, fixed "reply missing" text |
| Settled Started, exit 0 | client verifier (postcheck with the fact) → Success only on the exact target match | **Unverified** with the fault's text (no verification) | Unverified, fixed "reply missing" text (no verification) |

- **Recovery text (every required warning retained):** SetupOverride / RootWritable → their stopped messages ending in `UntrustedFolderRecoveryStep` (never `choco upgrade` / `--force`); WatchFailed → `StoppedWatchFailedMessage` (the `--force` repair advice); ReleaseIncomplete alone → `NotVerifiedReleaseIncompleteMessage`; a watchdog kind **plus** ReleaseIncomplete → that kind's stopped message (its action advice takes precedence; the untrusted-folder advice is never replaced by `--force`) followed by the fixed `ReleaseIncompleteAlsoNote`. History recognises each fixed message, including the three combined ones.
- **Verifier.** The client verifier calls a new `ChocolateyClientUpdatePostcheck.Evaluate(result, ReviewedClientRunFault fact, source, target, sid)` overload; it applies the fact first exactly as the binding overload does (watchdog verdict, then ReleaseIncomplete) and is the only `src` entry besides the helper-side binding overload; `EvaluateForTests` stays banned. There is no free-enum overload reachable from `src`.

### 8.4 Compatibility and versioning

- **(a) Package route unchanged.** Responses for `ChocolateyMachineRuntimeLimitsV3` (and every non-client route) never carry the property: `CreateResponse`/`TryReadResponse` keep their signatures and the package shape, so their bytes are identical and every existing golden and codec test stays unchanged. A package-shape reader rejects a frame that carries the field (new negative test).
- **(b) New desktop, older helper.** An older helper never admits the client route (A1 → `RequestNotAdmitted`); its 20-property refusal fails S14a under the client shape → Uncertain, never Success. In practice the desktop never sends the client route to such a helper: `Supports` (before the claim) requires the deployed capability token `Update/ChocolateyClientSelfUpdateV1`, which older capability files lack and the current allow-list rejects. The field is therefore only ever produced by helpers that know it.
- **(c) Older desktop, new helper.** Older desktops never send the client route, so they never receive a 21-property frame; package-route exchanges between any old/new pair are byte-identical and stay interoperable.
- **(d) Version.** Protocol value stays `"2"`, following O1: the change is additive and scoped to a route no deployed pair has ever exchanged, and the route-scoped capability token (ADR-022 manifest) is the version gate for the client shape. Allocating `"3"` would orphan `"2"` for the unchanged package route. The fact-extension record (rev 3) is extended by this section, not rewritten; reviewers may still choose `"3"` before admission, which would only change `ProtocolVersion` and the capability file.

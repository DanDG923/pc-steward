## Diagnosis and decision to make

The candidate and installed desktop DLL differ in CsWinRT AOT-generated types/reference ordering, with three differing generated-source document hashes in the portable PDB. Handwritten source document hashes, XAML type information, assembly references, XBF/PRI and the other non-signed payload files match. The output/staging-path explanation is disproved: both DLLs embed the same repository obj PDB path. The installed DLL equals the repository's shared `obj` output, showing that protected final staging did not isolate compilation intermediates.

The parent reran Opus's metadata and PDB tools successfully and confirmed those facts. Cross-compiler-process generator nondeterminism remains a hypothesis; no repeated-build experiment has proved that mechanism. Functional similarity does not replace byte identity and does not authorize accepting the mismatched installation.

There are two plausible remediation directions. Forcing reproducible generator output would require proving and fixing the generator/process behavior; disabling an interop optimizer would change the product compilation. **Recommended: remove compilation from the privileged deployment route and consume the already reviewed, pinned unsigned payload.** This directly preserves exact artifact identity and removes shared user-writable build intermediates from the signing path. It requires a narrow ADR-022 amendment and revised installer/validator fixtures; no product runtime feature changes are needed.

## Proposed file and interface boundary

| File / interface | Proposed responsibility |
|---|---|
| `scripts/Install-OwnerOnlyProtectedTestDeployment.ps1` | Retain `-Install`, elevation, same installing SID, collision refusal, fixed roots, mutex, certificate journal and transaction-owned recovery. Replace `dotnet build/publish` with required `-CandidateRoot`, `-CandidateManifestPath`, `-CandidateManifestSha256`. Never build or execute files from candidate/manifest. |
| Candidate producer | Existing local preparation generates the flat JSON array of `{path, bytes, sha256}` for the complete unsigned payload. The owner reviews/pins the raw manifest SHA-256 and source/test snapshot independently of deployment. |
| Candidate consumer | Installer authenticates the exact manifest bytes by the approved SHA-256, validates the whole path/content set, copies to a new protected staging tree, then revalidates the complete staged tree before creating/reusing a signer. |
| Focused `scripts/OwnerOnlyPayloadIntegrity.ps1` helper, if needed | Shared pure validation/copy-integrity and executable-image identity routines consumed by installer and read-only validator; no elevation, signing, launch, deletion or arbitrary command interface. Pin its hash alongside callers. Exact names/signatures are to be finalized before editing callers. |
| `scripts/Test-OwnerOnlyProtectedTestDeployment.ps1` | Preserve existing protection/signature/hash/resource checks; additionally verify protected pinned-candidate provenance, unchanged non-signed files and executable image identity for the new route. Explicitly distinguish legacy v6 evidence from the new pinned-payload route. |
| Existing remover | Preserve the fixed-root, same-SID, protected-ledger and separately approved destructive recovery contract. No new removal root or broad certificate cleanup. Only update recognized state if a schema change is required and covered by fixtures. |
| Focused synthetic fixtures | Test production integrity functions against isolated temporary payloads and malicious/changed inputs; never use installed roots, live data or real certificate creation as fixtures. |

The consumer accepts an exact local payload, not an unrestricted installer URL/package ID/script command. Paths must be absolute local filesystem inputs. The manifest hash is supplied through the reviewed action-time command, not learned from the candidate directory/database. A manifest alone is not owner approval.

## Proposed validation and transaction order

1. Validate explicit authority switches, manifest hash syntax/length, installing identity/elevation and unchanged allowlisted destination roots under the existing deployment mutex. Continue to refuse any existing installation/state; no in-place replacement mode.
2. Read bounded manifest bytes and require the approved raw SHA-256 before using entries. Require well-typed size/hash fields, a closed file-entry shape and an exact relative path set. Reject rooted/UNC/drive-relative paths, traversal, alternate data streams, wildcard/device/reserved names, ambiguous normalization, duplicate/case-colliding paths and file/directory collisions. Required desktop/helper/ScheduledHost and XBF/PRI resources remain mandatory.
3. Reject reparse points at roots/ancestors/descendants and directory traversal escapes. Read source files through stable read-only handles, verify resolved paths stay inside the approved source, and prevent concurrent file writes while copying. Do not recurse into a source reparse point. Candidate file count/sizes/content must match exactly, with no extra hidden file/directory payload. A changed or inaccessible input fails visibly.
4. Create a collision-failing transaction-owned protected state/staging tree using the existing ACL rules. Copy content only. Apply and verify exact administrator/SYSTEM ownership/write protection and Users read/execute on every staged path; then compare the staged full path set, lengths and all SHA-256 values with the pinned manifest. Only staged bytes may advance. No source `obj`/`bin`, compiler server, build project, source-control command or SDK is involved in privileged payload production.
5. Require both candidate executables unsigned before signing. Record their reviewed SHA-256 and a verified signing-invariant image identity. Only after all staged checks pass may the existing journaled 14-day temporary certificate route mutate CurrentUser My/Root/TrustedPublisher or reuse an explicitly approved existing certificate.
6. Copy verified staged bytes to the fixed installed root; protect and revalidate them before signing. Sign only `PCSteward.Desktop.exe` and `PCSteward.ElevatedHelper.exe` with the approved signer. Require Valid same-signer Authenticode validation. Require signing-invariant executable-image identity equal to each staged unsigned executable, proving the signed executable corresponds to that approved image; preserve a strict full-byte check for every other file.
7. Record the approved unsigned manifest hash, complete unsigned manifest/provenance, executable image identities, exact signed installed manifest and signer in the protected ledger. The independent validator reads protected evidence, not a mutable candidate directory. Missing/malformed new-route provenance fails. Existing legacy-ledger validation/removal remains explicit and separately identified, without claiming the new artifact guarantee for a legacy install.
8. Run existing trusted-deployment checks plus the new candidate-origin checks before success. Use existing transaction-owned rollback/incomplete-ledger behavior on installer failure. Retain exact failure visibility; no automatic caller retry. Never launch PC Steward or create/change its per-user data/schedule.

Signing-invariant identity must cover the executable image, resources, debug/import information and other relevant content; validating a signature or comparing only code sections is insufficient. Prefer a documented Windows signing/subject-interface facility and verify unsigned/signed parity with tamper negatives. Microsoft documents `ImageGetDigestStream` flags for debug/resources/import information and requires serializing ImageHlp calls: [Microsoft API reference](https://learn.microsoft.com/windows/win32/api/imagehlp/nf-imagehlp-imagegetdigeststream). That documentation alone does not establish complete equivalence to Authenticode SIP hashing or coverage of appended non-PE bytes. Implementation must prove the chosen mechanism's coverage and reject unexpected unsigned overlays/signing mutations rather than assume it. Unsupported or unproven equivalence blocks signing/acceptance.

## Meaningful verification required before a new host plan

- Write focused fixtures first and observe the relevant missing-behavior failures, then implement the smallest coherent change.
- Exact good payload accepted without build/publish; changing any byte, length, approved manifest hash or path set fails before signing. Extra/hidden files and missing PRI/XBF/helper/ScheduledHost fail.
- Malformed/oversized entries, duplicate/case/path aliases, traversal/ADS/device names, junction/symlink/file/root substitutions, concurrent file replacement and source-to-staging drift fail closed. Exercise actual supported Windows filesystem behavior with isolated fixtures; report unsupported fixture coverage honestly.
- After the source changes or disappears, the frozen staged copy must still correspond to the approved manifest. The signed-image check rejects changes to executable code/resources/debug/import/overlay data and proves only permitted signing transformations can pass. No live signer/store mutation is authorized for these tests; use synthetic fixtures or a separately approved signing fixture if indispensable.
- Independent validator rejects missing/tampered new-route provenance and mismatched signed-image/non-signed-file identities while preserving explicit legacy protection validation. Malformed/incomplete ledger and separately guarded removal retain their safety contracts.
- Fix the caller's null-exit-code capture separately, with isolated child processes returning known success/nonzero codes; capture a real native exit code, never infer success from null. This is logging correctness, not a reason to rerun the existing installation.
- Run the narrow focused fixtures, canonical Release build and full suite on SDK 10.0.403/approved PowerShell fallback; inspect diff for scope, command/path/trust expansion. Obtain a fresh independent consultation/review of the changed route, pinned scripts/helper/tests and evidence.

The suggested repeated compiler-process experiment is optional diagnosis of the unproven generator mechanism. It is not necessary to justify keeping builds out of deployment and must not replace artifact-consumption tests or weaken the exact gate.

## Later host authority remains separate

Accepting this proposal permits local implementation/tests of the amended route; it does **not** approve removal, certificate cleanup, redeployment or launch. Before any revised host approval request, finish the code/fixtures/review and present exact script/helper hashes, approved candidate/manifest, retained installation/ledger/signer baseline and preservation/rollback plan.

The next host plan would need explicit approval for removal of the retained failed-identity deployment with the existing guarded remover, followed by one installation of the exact reviewed payload through the changed route. Reusing the current candidate is possible only after revalidating it; do not silently adopt the installed DLL hash as the new candidate. Current signer/root removal and any new signer creation must be disclosed. Launch remains separately approved after all identity/protection gates pass.

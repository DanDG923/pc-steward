## Dialogue and objections

1. Opus round 1 proposed typed progress, an observer channel and unchanged protocol 1, initially subject to an owner scope decision. The main agent challenged the conditional-version interpretation, a Domain-to-Application dependency, and sequence gaps caused by coalescing.
2. Opus round 2 accepted Path A within existing task authority and placed the types in Application. It proposed assigning sequence at emission, keeping final history authoritative, and retaining warning-time cancellation without adding an in-flight installer cancel UI.
3. The main agent objected to Opus's proposed telemetry-only interpretation of overflow cancellation: accepted Q1 explicitly says to boundedly cancel on overflow. The main agent also rejected guarantees for arbitrary blocking observers, a four-frame burst plus a guaranteed 250 ms terminal delay, and an eight-second 32-terminal flush presented as a bounded responsive teardown.
4. Under the owner's standing escalation rule, Fable 5.1 and ChatGPT Astra 6 joined the dialogue. Astra agrees that telemetry-only cancellation lacks explicit policy authority. It proposes a pull mailbox with one coalescible nonterminal and separately reserved terminal, fixed route transitions, and true operation cancellation only for a capacity fault. Normal slow/unread UI consumption would never cause overflow. Its findings and the main agent's source checks were returned to Fable's ongoing discussion.
5. Fable incorporated Astra's findings and proposed separating Q1's two fault classes: reject/degrade sequence faults; capacity overflow cancels a per-item linked operation token with a distinct overflow reason and verification-required outcome after possible invocation. It noted that existing provider output overflow and helper timeouts already attempt termination, and that a new internal item token is necessary because the current UI passes CancellationToken.None. The main agent accepts this distinction and the in-scope relabelling of the premature Running diagnostic; it does not accept that a bounded wait alone proves no orphan readers/processes or residual external installer work. Fable proposed bounded termination/reader waits with explicit unconfirmed teardown; this is returned to Opus and Astra for further objections before implementation. Opus remains a participant, not replaced by escalation.
6. Astra's follow-up accepts the two-class design and item token. It distinguishes telemetry detachment from execution safety state; after terminal commitment offers close without retroactive cancellation, foreign identity never charges this item, and identity-matching rejected attempts still consume the defensive budget until a capacity fault latches once. Owned reader/exit-wait/timer tasks must be observed, not abandoned behind `WaitAsync`.
7. Opus round 3 received Fable/Astra findings and withdrew telemetry-only overflow cancellation. It accepts the stricter attempt-count interpretation, asynchronous fault signalling (no arbitrary callbacks or token cancellation inside a producer lock), pull consumption, and a separate session-owned residual-work latch that telemetry detach cannot clear. It proposes observing owned completion or retaining ownership/latch until completion, while explicitly disclosing external-installer and restart/cross-session limits of the existing Update route. The main agent accepts that scope distinction for unchanged protocol-1 authority and will not claim the stronger new-operation barrier is implemented. A five-second Update teardown-attempt budget would be an implementation choice to validate, not an inherited Update execution deadline. Real owned-I/O fixtures precede any teardown claim. Opus sees no owner decision blocking this route; this is design agreement on the approach, not proof the implementation exists or a gate passes. Fable's follow-up on remaining ownership mechanics is pending.

## Allocated first progress interface — before implementation

New `src/PCSteward.Application/UpdateProgress.cs` owns `UpdateProgressPhase`, `UpdateProgressCompletion`, `UpdateProgressOfferResult`, `UpdateProgressFrame`, `UpdateProgressMailbox` and internal `UpdateProgressQuota` / `UpdateProgressEncoding`. The Application coordinator will produce fixed phase offers and publish a recorded final only after its history write; Execution adapters will later receive a job-bound producer handle. The Desktop will consume `UpdateProgressMailbox.TryTake(out UpdateProgressFrame?)` on its dispatcher, not through execution callbacks. Caller plumbing and that producer-handle interface are a subsequent edit boundary, to be recorded before those callers change.

Mailbox construction binds job/correlation GUIDs, User or Machine route, and an optional monotonic TimeProvider. Internal `Offer(jobId, correlationId, phase)` returns a closed offer-result enum; `Complete(status?, completionKind)` reserves/preserves the single terminal; `SealProducer()` ends further production without dropping retained data. A separate asynchronously continued `CapacityFault` task signals one latched fault without invoking cancellation callbacks from the mailbox. Snapshot counters are bounded value types, not repeated free-form logs. No cancellation/installer authority is implemented by this pure component.

The closed local schema is canonical UTF-8 with fixed field order: jobId, correlationId, sequence, phase, finalStatus, completion, degraded. GUIDs, bounded integer/enum values, nullable closed final status/completion and a boolean only; no provider text, path, percentage or command. This is **local progress schema 1**, not a change to helper protocol 1 or an IPC capability. Sequence is assigned only on successful take; emissions are separated by at least 250 monotonic milliseconds. Two slots (coalescible nonterminal, reserved terminal) are below Q1's 32-frame bound. Matching offers 1–255 consume the defensive attempt budget before phase validation; 256 faults once, leaving terminal capacity. Foreign identity does not consume this job's budget; after terminal all production closes. Actual canonical bytes are counted conservatively at maximum sequence width before admission and checked at emission; 512 bytes are reserved for the fixed terminal, with fixtures proving every legal terminal fits. The separate real-byte quota primitive enforces 16 KiB/frame, 1 MiB/item and 32 pending, and its exact/one-over tests are distinct from the proof that fixed production frames cannot approach these limits.

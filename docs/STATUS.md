**Diagnostic timeline, Task 64 stage 3: Windows readers (2026-11-13; code and tests; no host action).** Requirement: `FR-DIA-01`. New project `PCSteward.Diagnostics.Windows` ([plan](review/TASK_64_DIAGNOSTIC_TIMELINE_PLAN.md)).

- **Event logs.** System (Kernel-Power 41, EventLog 6008, BugCheck 1001) and Application (Application Error 1000, Application Hang 1002, Windows Error Reporting 1001) through one structured wevtapi query each: provider, event ID and time window applied by Windows, newest first, rendering only identity, time and Kernel-Power 41's bugcheck code.
- **Reliability.** Narrow, time-filtered WQL on `Win32_ReliabilityRecords` naming six properties and the allowlist, through WMI's own COM interfaces with a 250 ms wait per result so a stalled provider can't hold the reader. WQL cannot order, so the reader walks back from the end of the window in stretches that double from one hour and keeps only stretches that fit whole, which always gives the newest records. Every record materialized, including discarded ones and the one that proves more matched, counts against the source's slots; the first stretch that doesn't fit ends the read and the source is reported as truncated. The product name is the only text kept.
- **Windows Update history.** `QueryHistory` pages read from the local history store, stopping at the window, the slot count or 2,000 entries. Nothing is searched, downloaded or installed. `ConnectServer` and the Windows Update calls are synchronous with no timeout, so each route allows one call at a time app-wide: while an abandoned call is still running, a later collection reports that source as not read instead of starting another.
- **Tests.** `WindowsDiagnosticReaderTests` (queries, projections, paging bounds, status, the orchestrator with all four sources; one CI smoke run proves Windows accepts both event log queries) and `DiagnosticReaderBoundaryTests` (only Application referenced, only six wevtapi calls and two COM classes, no write, search, install, file, registry or process access, never referenced by the scheduled host). **UI review follow-up 3: alignment measured from drawn pixels, and calm wording for a healthy cache (2026-11-13; code and tests; rides the next release).** Requirements: `AC-UX-01` (best effort), `FR-UI-01/03/05`. Owner reports after installing 0.1.15: "Check for updates" was still taller than the button beside it with its label higher; the step numbers 1, 2 and 3 sat at the top of their circles; the app's name in the title bar sat higher than the window buttons; and Updates showed a yellow "Cached results" warning 11 minutes after a healthy check while Home read as calm. The badge fix from follow-up 2 was confirmed on the owner's display.

- **Why the earlier fixes missed.** Follow-ups 1 and 2 reasoned about layout boxes. A box says where a control is, not where its letters are drawn. The Windows launch check now reads the drawn pixels: with `PCSTEWARD_LAYOUT_SAMPLES=1` (set only by that check) the About page also shows a card of sample controls built by the same code the pages use, and the check logs where their ink is (`LAYOUT-INK`) and a verdict for each (`LAYOUT-INK-VERDICT`). The samples are inert and never shown in a normal start.
- **Cause, the icon button (measured at 100% on a Windows build).** A plain button is 32 high with its label's baseline at 20. A button whose content held an icon and a `TextBlock` was 33 high with the baseline at 18. The icon is not the cause: a `TextBlock` used as button content is one unit taller than a button's own label and draws its letters two to three units higher. At 150% that is the owner's 51 against 48 pixels.
- **Fix, the icon button.** `StewardVisuals.IconLabel` puts the label in a `ContentPresenter` (`StewardVisuals.ButtonLabel`), which is how a plain button draws its own label. The review step's administrator button, which built its own icon and text, now uses `IconLabel` too.
- **Cause, the step numbers and the title bar name.** A text box sized to its capital letters (`TextLineBounds.Tight`, line height 0) centres its letters only when the font is named. With the default font the letters draw at the top of the box: the step digit's ink was rows 3 to 9 of a 24-unit circle. The title bar name was a plain caption, 1.5 units above the mark and the window buttons.
- **Fix, cap-height text.** `StewardVisuals.CapHeightBox` sets the tight bounds, line height 0 and centring, and names the body font when no style does. It is used for the step numbers and step labels, the title bar name, text beside a badge (`CapCentred` calls it) and, in the Installed apps row template, the status chip's label, which had the same fault.
- **A long name on a button.** A one-app button names its app only when the name is 24 characters or fewer (`UpdatesPagePresentation.LongestNameOnAButton`); otherwise it reads "Update 1 app…" (Home, Updates header) or "Update 1 selected…", and Home's accessible name still says which app.
- **Cached results (owner's choice, 2026-11-13).** Results read back from the database are always marked cached, so both pages called an 11-minute-old healthy check "Cached", and Updates showed it as a warning. Now, in `FreshnessPresenter`: results of a successful check inside the existing 15-minute live window read as live on both pages; older results read "Cached: these are the results of the last check." with an information tone; the warning tone and "results may be out of date" are kept for a check that failed and fell back to the cache, a source that never succeeded, or results more than 7 days old (`FreshnessPresenter.StaleAfter`). `FR-UI-05` still holds: the last check time and live or cached are always shown.
- **Tests.** `HomeActivityDecisionsPresentationTests.RecentResultsReadAsLiveAndOnlyAFailedOrWeekOldCheckWarns`; `UpdatesAndJobPresentationTests.UpdatesHeaderStatesCountsFreshnessAndOffersTurningOnChecks` (notice tone and words, button labels); source contracts `UiAccessibilityContractTests.ActionRowsWrapAndTheWindowHasAMinimumSize`, `ABadgeIsLevelWithTheTitleBesideIt` and `AlignmentIsMeasuredFromDrawnPixelsOnSamplesOnlyTheLaunchCheckShows`.
- **Measured after the fix (Windows launch check, 100%).** An icon button and a text button are both 32 high with the label's ink on the same rows (`tallerThanTextButton=0 labelHigherThanTextButton=0`), in both button styles, and the real "Copy diagnostic" button on About is 32 high. The step numbers and labels are within one unit of the middle of their circles (the numbers were 5.5 units above it); a step number also has one unit of space under it, because the first measurement after the fix found it one unit low. A title and the badge beside it have their ink on the same middle line. The title bar name's ink is half a unit from the middle of the mark and of the window's Close button (it was 1.5 above).

**Diagnostic timeline, Task 64 stage 2: snapshot storage and the PC Steward history source (2026-11-13; code and tests; no host action).** Requirements: `FR-DIA-01`, `FR-DIA-03`, `FR-DIA-04`. Schema version 13 ([plan](review/TASK_64_DIAGNOSTIC_TIMELINE_PLAN.md)).

- **Storage.** Three tables hold whole immutable snapshots: one row per snapshot, one per source result and one canonical JSON record per row. Saving removes expired snapshots, then the oldest unprotected ones until the 64 MiB total fits, all in one transaction, and reports how many were pruned early. Expired snapshots are never listed or loaded, even before deletion. Loading is all or nothing: a row that does not parse back to its exact canonical form, a missing record or a size mismatch makes the snapshot unreadable rather than shorter.
- **Lifecycle.** Clear scan data deletes every snapshot and counts them in its summary; Clear update history leaves them unchanged, because each snapshot owns its copy of the history it captured; factory reset already deletes the database.
- **First source.** `PcStewardHistoryDiagnosticReader` reads PC Steward's own recorded update history in the window, newest first, with the app's current display name (or package ID), versions, typed outcome, exit code and the already sanitized diagnostic.
- **Stage 1 review fixes.** A reader is now started on the thread pool and waited on for only what remains of its share, so one that blocks before its first await cannot hold the collection. Identity tokens of one character are redacted too.
- **Tests.** `DiagnosticSnapshotStoreTests` (SQLite), the strict stored-record parser, a synchronously blocking reader and a one-character name.

**UI review, part 5c: real app icons, for release 0.1.14 (2026-11-13; code and tests).** Requirements: `FR-UI-01`, `FR-INV-01–04` (the scan is unchanged), `FR-DAT-12` (no new stored data), `AC-UX-01` (best effort). Item 20 of the UI review, the last one. The owner chose option A of [ADR-035](adr/ADR-035-REAL-APP-ICONS.md) on 2026-11-13, so the record is Accepted. Presentation only: no scan, match, decision or update rule changes, and nothing new is stored.

- **An app's own icon in place of the two letters (item 20).** Home's ready updates, the Updates groups, the Installed apps list and app details show an app's own icon when one can be read, and the two-letter tile otherwise. A Store-type app shows the logo Windows' package API returns for it. A classic app shows the icon its uninstall entry names in `DisplayIcon`. The app's name is still beside the icon and is still what a screen reader reads; the icon is decoration.
- **What may be read.** Only the desktop app reads icons, without administrator rights, and only for a tile that is on screen: a row further down a page, in a closed group or built ahead by the list for scrolling reads nothing until it comes into view. `DisplayIcon` is read from the uninstall entry the scan recorded and from nowhere else, without expanding environment variables. The path must be a full path to an `.ico`, `.exe` or `.dll` on a fixed local drive. Network paths, mapped and removable drives, device paths, stream names, relative paths and values with an environment variable are refused. So is any path that passes through a link of any kind (junction, symbolic link, cloud placeholder): links are refused, not followed.
- **How it is read.** The file is opened for reading only. One icon image is taken out of its bytes by a small bounded reader, and only that image (at most 1 MB) is given to Windows' image decoder. The file is never run, never loaded as code and never handed to the Windows shell, so no other program's icon handler is loaded. Up to four reads run at once off the UI thread. A read slower than two seconds is not waited for; it keeps its place among the four until it ends, so stalled reads can never number more than four.
- **What is kept.** Icons are kept in memory for the session, up to 512. Nothing is written to PC Steward's data folder, the `DisplayIcon` text is not kept and nothing is sent anywhere. About's privacy text says so. The scan still reads the same five registry values; the elevated helper and the scheduled check have no icon code.
- **When it fails.** Any refusal or error leaves the two-letter tile and is not reported. Installed apps reuses its rows as it scrolls; a row starts again from its letters, and an icon that arrives late is shown only if the row still holds the same app.
- **Tests.** `AppIconRulesTests` (8: which entry, `DisplayIcon` parsing, refused paths, fixed drives only, links refused, size and limits, when a tile is on screen) and `AppIconFileTests` (4: `.ico` and 32-bit and 64-bit program files, the icon a number names, truncated and overwritten files give nothing, only a seekable stream is read), all portable. Source contracts `AppIconBoundaryTests.OnlyTheDesktopListsReadAnAppsIcon`, `TheIconReaderOpensAFileAsDataAndKeepsNothing` and `TheTwoLetterTileIsTheFallbackAndTheIconIsDecoration`. The Windows launch smoke test logs how many rows of Installed apps showed an icon after its scan, each on-screen row against the icon its uninstall entry names, and whether the details column showed the opened app's icon; it fails if the app stopped while showing icons.
- **Accepted residual (independent review).** The link check and the file open are two steps. A program already running as the owner that can create links could swap a folder for a link in between. It could open the same place itself, so no boundary is crossed; ADR-035 "As built" records why this is not closed.
- **Not claimed.** The desktop reader, the Store logos and the image decoding compile and run only on Windows: they are checked by the Windows build and the launch smoke test's count on a runner, not yet on the owner's PC or display. How a Store logo with its own background plate looks on the tile has not been seen. Icons are not kept between sessions, so each is read again after a restart. An app installed through a link, on a removable or network drive, or that names no icon keeps its letters.
- **Next.** The UI review's 21 items are all built. The release that carries them is cut by the release thread.

- **Tests.** `WingetPostUpdateRegistryLinkTests` (link rules, non-WinGet jobs, failed and slow reads) and `ReInventoryAcceptsTheEntryWinGetLinksAfterAnUpgradeReplacedTheReviewedOne` (replaced entry accepted; no link, a link to another key, the old entry still present, wrong architecture or version all rejected).

Their visible uninstall entries sit in the 32-bit registry view (read as x86, against x64 updates), and each runtime's DisplayVersion (8.0.33.36622) differs from WinGet's (8.0.33). Each runtime also has a hidden MSI entry (`SystemComponent` = 1) with the same name and an internal version (64.132.61678), which made the name match ambiguous. **WinGet update compatibility evidence for release 0.1.6 (2026-11-13; code and tests; found by the D4b stage 4 host check).** With 0.1.5 the WinGet source worked on the owner's PC, but no WinGet update was ever offered: even after the owner confirmed a package identity, the app stayed "Update available — review" with `MissingArchitectureEvidence`, `MissingScopeEvidence` and `MissingChannelEvidence`. The owner chose to accept same-name, same-publisher matches. The same structured read now also returns the catalog publisher and WinGet's installed product code: a single product code links the uninstall entry with that key name as provider-supplied evidence, and a unique same-name, same-publisher (Medium) match is actionable when nothing else needs review. Unknown installed scope or architecture is now review only, and one uninstall key with different targets in several registry views is ambiguous.
